This is my write-up of episode 10 of This Week in Open Lakehouse, the weekly show Scott Haines and I host on open source data engineering news. I recorded this one sick (coughing, drinking Gatorade between sentences) while Scott's dogs barked at a neighborhood cat, so if you'd rather read than listen, I genuinely don't blame you; the video is above, and the audio, show notes and full transcript are further down this page.

We opened on something that wasn't news at all, which was AI code review. Scott's experience is that agents now catch bugs a human reviewer would have missed for years, and mine is that the review bots on my Spark pull requests keep proposing things that make sense for the diff and no sense for the project. A bot doesn't know why a behavior was copied from an older implementation on purpose, or that the extra scope it's suggesting already has its own JIRA, so if you let two agents argue it out you either get a full feature nobody asked for or you end up back at the original decision (which, to be honest, has happened to me). The bots aren't wrong about the code; they're missing the history, because the history was never written down anywhere they can read.

**That turned out to be the theme of the whole week: most of what moved in the open lakehouse was a project writing down something that used to live in people's heads (how a materialized view should behave, what a serialized payload is, how to reference a file from an Arrow array, how a client talks to an engine), because a written specification is the only kind of project context that a new contributor, a different engine and an agent can all follow without asking the person who knows.**

## Spark: GraphFrames is back, and real-time mode goes after batch

GraphFrames coming back into Spark is the happy story of the week. Spark had graph processing in the main distribution once (GraphX), let it decay into a deprecation, and meanwhile Sem kept GraphFrames alive as a separate package that people actually use for things like connected components; the [vote to bring it into Apache Spark](https://lists.apache.org/thread/ymqj7q2vmxdbcd7m61nz06rv6kbqx2dl) passed with no objections and a long list of binding votes. What I like about this is the direction of travel: a library earned its way back by being well maintained outside the project, rather than being kept inside it out of inertia.

The proposal I'm still wrapping my head around is Cheng Xu's SPIP to [extend real-time mode to distributed batch SQL and DataFrame queries](https://lists.apache.org/thread/db86x3yx97okrkklfyfc6obo59mvzoqn). Real-time mode arrived for Structured Streaming in Spark 4.1 and got stateful operators in 4.3; it works by keeping long-running tasks connected so data flows between stages instead of waiting on a materialized shuffle. The SPIP's argument is that agents now issue a lot of short SQL queries (retrieval, feature generation, ranking, analytical tool calls), that each query's latency is directly the agent's response time, and that a materialized shuffle boundary makes every downstream stage wait for upstream output it could have started consuming already. So the proposal lets the planner pick eligible batch shuffle boundaries and stream through them, with explicit opt-in, bounded buffers and admission control so a cluster under pressure still makes progress, and with materialized shuffle remaining the default.

The early numbers are a 1.64x speedup on distributed TPC-H Q3 at scale factor 10,000, with physical shuffle writes down 95.6%, and the author is careful to call these workload-specific rather than a general claim. The initial scope is short, read-only queries where restarting the whole query after a transient failure is acceptable, which is exactly the shape of an agent's tool call and exactly not the shape of a nightly ETL job, and I think that framing is the honest part of the proposal. The [vote passed](https://lists.apache.org/thread/b7mwv5vdj06m74k5gs5vqhddrfkxfm3m) a few days after we recorded. My guess on the show was that it targets 4.5, since 4.4 was [cut on November 16](https://lists.apache.org/thread/z46kvby3oh32lz2obkntbqwpcwjj7c3s), but that depends entirely on how far along the prototype is.

Two smaller Spark notes: Huaxin Gao proposed the [first Spark community sync](https://lists.apache.org/thread/r8ms8fgfvtr0zr3hmxn7p01fb8lry352) (a recurring virtual meeting in the style Iceberg already runs), and the [Swift](https://github.com/apache/spark-connect-swift) and [Rust](https://github.com/apache/spark-connect-rust) Spark Connect clients both moved to 4.3. The Swift client is the one that got Scott's attention, since it means a Spark Connect session from an iPhone is a real thing you could do, and I'm already working on a post where I put a Connect client on my phone and then on whatever other device in my apartment has enough memory to embarrass itself. Further out, someone in the community has been prototyping a Spark Connect client in WebAssembly, which is not production ready but would let an agent in your browser run Spark SQL directly; Scott's point was that a browser with a few tabs open already holds more memory than a modest Spark driver.

## Specs everywhere: Iceberg views, Parquet types and Arrow's FILE type

Scott walked through views on the show as though Iceberg's view specification were new, and the correction is worth making because it sharpens the point. Iceberg has had a [view spec](https://iceberg.apache.org/view-spec/) for a while (a view stored in the catalog as metadata, with SQL representations per dialect, readable by Spark, Trino and anyone else); the news this week is that the materialized view working group has a [materialized view spec ready for broader review](https://lists.apache.org/thread/zpl1pk6v7k49s30gmm3kr986bc9y7jyv). That's the harder problem, since a materialized view has to say not only what the query is but how fresh the stored result is and when an engine is allowed to trust it, which is precisely the kind of thing that, without a spec, every engine answers differently.

I tied this on the show to Iceberg's file format API, which lets you register a file format with Iceberg in a way every engine can read without bespoke readers and writers, and to Spark Connect, which does the same for clients. I almost credit the Iceberg REST catalog with starting this trend: once a REST spec became the backbone for catalogs, projects started noticing that adhering to a spec frees everyone from caring which language, which format or which engine is on the other side. Scott added the agent angle, which I think is the strongest argument for all of it; give an agent a specification with correct examples and failure codes and adding support to a project is close to a single task, whereas without one the context has to be reverse engineered from another code base or pried out of the one person who remembers.

Parquet is where the specs got concrete. Neelesh Salian split a [SERIALIZED_VALUE logical type](https://lists.apache.org/thread/5xn8o9rvrv1rsjs811t2gn0tkjq0zl02) out of his larger WIRE proposal, so a binary column holding serialized messages (Protobuf, Thrift and the like) can record what format the bytes are in and carry their schema, while readers that don't know the type fall back to plain bytes. Scott replied on the thread with the use case he lived at Twilio, where lots of Protobuf ended up in Parquet as a cheaper place to keep Kafka history than Kafka itself, and nobody had a standard way to say what those payload bytes were. Alongside it, Arrow is discussing a [canonical extension type for FILE](https://lists.apache.org/thread/pp51hdow3gr51654ywfhffwsk22ywcnz), so an Arrow array can carry typed references to files through an Arrow-native pipeline without losing what they point to; the two proposals solve neighboring halves of the same problem, which is carrying meaning along with bytes without a separate registry to look it up in.

The rest of the Parquet news is momentum. The [Java implementation of ALP encoding](https://lists.apache.org/thread/z99rnt1z9lw0j194tr1tjxjsf4nkoq0q) (adaptive lossless floating point compression) merged, following the discussion Andrew Lamb has been driving, and Russell Spitzer, already an Iceberg PMC member and seemingly involved in every project at once, became a [Parquet committer](https://lists.apache.org/thread/fzxrc5bg8xqzgxoop6qsh3v7w1ly5k7f). I said on the show that Parquet has been in overdrive this year, and I keep being surprised by it, since a format this widely deployed is exactly the kind you'd expect to move slowly; every change ripples through every engine, which is presumably why so much of the work arrives as specs first.

## DataFusion adopts datafusion-distributed

DataFusion (which is [voting on 56.0.0 release candidates](https://lists.apache.org/thread/v4hbb0tl2fyfx4lto8l4rcyws1gl5m6b) while Spark is on 4, a versioning gap that still makes me laugh) [voted to accept datafusion-distributed](https://lists.apache.org/thread/2fp01v8jtx97jolpbrjloggntt46hjfr) as an official subproject, moving it out of datafusion-contrib. The interesting part is that DataFusion already has a distributed engine in Ballista, and the two are deliberately different shapes:

| | datafusion-distributed | Ballista |
| --- | --- | --- |
| What it is | A library that adds distributed execution to an existing DataFusion application | A complete distributed query engine |
| The plan | A normal DataFusion physical plan with extra nodes that stream Arrow between machines | Its own scheduler, executors and clients |
| Workers, networking, deployment | Left to your application | Provided |
| Choose it when | You already run DataFusion and want to scale it out without adopting a platform | You want an engine with operational tooling, materialized intermediate results and task recovery out of the box |

If it graduates fully, the implication is a Rust-native path from embedded analytics to distributed execution inside one project's lineage, which is a nicer design story than wrapping a JVM engine (not that anyone would ever do that with Spark).

## Everything else we covered

[Lakekeeper 0.15.0](https://docs.lakekeeper.io/about/release-notes/) added a `write` privilege that separates changing a table (data, schema, snapshots, `CREATE OR REPLACE`, dbt models) from dropping or renaming it, so a pipeline can write without being able to destroy. Scott's framing was that this is what production hardening looks like for a catalog you'd run a company on; small, unglamorous, and exactly the kind of invariant a consumer relies on.

Airflow shipped [Go and TypeScript task SDKs](https://airflow.apache.org/docs/apache-airflow/3.4.0/authoring-and-scheduling/language-sdks/index.html). One correction to what we said: on the show we called them 1.0 releases, and the accurate version is that both conform to the 1.0 Language SDK spec for Airflow 3.4 and later while the docs still mark them experimental. I said I don't know anyone who uses TypeScript, which I stand by as a statement about my friends rather than the language, but the larger pattern is real; between these SDKs, the Connect clients and Rust releases across Arrow, Paimon and Lance, data engineering is leaving its JVM-and-Python home, and I suspect the next fight is dependency compatibility across all those runtimes rather than the code itself.

Hudi opened [RFC-117](https://lists.apache.org/thread/9mzkzwcc75gcyn17pjkl0v9961kbbt1f) on packaging a lakehouse so agents can discover, query and write data without bespoke integration work, which we're tagging to follow. And if you want to be in the room for any of this, Iceberg runs a sync for nearly everything (indexes, UDFs, catalogs, Rust, Go, variant shredding); the [index sync](https://lists.apache.org/thread/mqpz7pfhztx79r5ok0m7j4r7l3yovktq) posts its summaries and recordings to the list, and the [UDF sync](https://lists.apache.org/thread/gm7pvw2cntp15mv86bvktq5vbnxmcso8) is going biweekly. They're friendlier to North American time zones, fair warning.

## Be nice on the dev list, it's permanent

My sign-off advice was to be nice on the dev list, partly because data engineering is a much smaller community than its footprint suggests (the same names show up across every core project, so you're stuck with these people for a long time) and partly because once a message is in the Apache archive it's out of your hands forever. Scott's version was simpler: if you're having a bad day, just don't post.

I think that's the same lesson as the review bots, from the other direction. The mailing list is the one place an open source project's history does get written down, permanently, which is exactly why it's the record a newcomer or an agent can go back and read; a spec is the deliberate, edited version of that record, and the week's work was a lot of projects deciding which of their decisions deserve one. The review bot that doesn't know why my pull request copies an old behavior won't be fixed by a better model; it gets fixed when someone writes the reason down.

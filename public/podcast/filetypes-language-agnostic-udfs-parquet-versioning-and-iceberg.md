# TWIOL #2: FileTypes, Language-Agnostic UDFs, Parquet Versioning, and Iceberg Updates

By Lisa Cao.

This is my write-up of episode 2 of This Week in Open Lakehouse, the weekly show Scott Haines and I host on open source data engineering news; the video is above, and the audio, show notes and full transcript are further down this page.

I opened the episode by warning everyone that it was a quiet week (people back from summer, threads from last time wrapping up, votes closing) with nothing super drastic, unless you happen to be really excited about types. Scott is, to be clear; he does nothing but message me about types all day. But reading the threads back for this post, I think I undersold it, because the types were the news, and they were the news for the same reason in every project.

**Once a dozen engines share one file format, one catalog API and one client protocol, the cheapest way to add anything new (a file, a nanosecond, a UDF written in Rust, a filter expression) is to define it once in the shared layer, along with a rule for what an older reader should do when it doesn't understand it; so the hard work this week wasn't writing features, it was agreeing on types, versions and fallbacks that everyone else can build on.**

## Parquet learns to say which version it is

[Parquet Format 2.14.0](https://lists.apache.org/thread/ovo7vhh2gp31v32xzq6wm5f0grk97bs3) passed its release vote, carrying the [FILE logical type](https://github.com/apache/parquet-format/blob/master/LogicalTypes.md#file), Adaptive Lossless Floating-Point (ALP) encoding and chronological ordering for INT96 timestamps. I said on the show that Parquet is a hard project to commit to, since it sits under nearly every production system and under Delta and Iceberg as well, and that's exactly why the more important thread this week was the one about versions. Today a reader can't cleanly tell which version of Parquet wrote a file, because the version was never encoded cleanly in the Thrift metadata, and with more and more new types and encodings arriving that ambiguity gets expensive. The community [voted](https://lists.apache.org/thread/rd271soqncrskd11kcr174gchd1vzpkc) to bundle forward-incompatible features (new encodings being the canonical example) into major versions: they accumulate "in preview" behind a writer flag, the community votes to close a version, and from then on writers can default to it while anyone stuck with an older reader pins the writer to the older version. The [finalizing thread](https://lists.apache.org/thread/bqn0f3w7v6vw0wkw7vp9zvss1bk8hco7) is now down to details like Ryan Blue's proposal to put the version in the magic bytes (`PAR3` for v3, and so on).

The companion piece is the rule for types a reader doesn't recognize, which [passed](https://lists.apache.org/thread/f1qgt2x0gg8ybwgcgshc67k1hso5t2qd) on its own vote rather than in the 2.14 release (one correction to how I described it on the show): a reader that meets an unknown logical type, or an unknown logical/physical combination, ignores the annotation and reads the column by its physical type. FILE is the cleanest example of why this matters, since it's just a group of ordinary columns (`uri`, `offset`, `size`, `content_type`, `checksum`, `inline`), so an old reader sees a struct of strings and integers and carries on. 2.14 also carries the result of a [vote to remove self-references](https://lists.apache.org/thread/cykmmq4ggd2thqkjcj888ywmsy50fgh1) from FILE before it shipped, because pointing at a byte range inside the containing file would have needed its own compression, encryption and size accounting, which is a second page mechanism nobody wanted to specify.

One more correction, this time to Scott: nanosecond timestamps and numeric vectors weren't both voted on. The [nanosecond vote](https://lists.apache.org/thread/v11pw7sbnkdxzjhkmcbsx06clyvjv0xx) passed (it lets the timestamp annotation sit on `FIXED_LEN_BYTE_ARRAY(12)` columns to cover the full SQL timestamp range in nanoseconds), while the vector type is still in [discussion](https://lists.apache.org/thread/kgmgn2vmrz49thbfhv8b66lglsyd81xt) about its physical representation. Scott's guess that they'll show up in 2.15 or later is fair either way.

## Spark gets a FILE type and a UDF protocol

The [FileType SPIP](https://lists.apache.org/thread/jgh4t8fp64vt1so8m7xv5wf103wyrx9m) from Burak Yavuz and Dejan Krakovic passed with no objections. Until now unstructured data in Spark had two paths: embed the bytes as a binary column, which doesn't scale for a 30-minute video (or a 30-minute recording of your two favorite YouTubers), or store the path as a string and hope everything downstream knows what to do with it. FILE holds the path plus a little metadata, and the engine, the file format and UDFs all understand it, so a query can filter, join and project files without reading them and load bytes only where it needs to; the SPIP says outright that it builds on the Parquet FILE type, which is the shared-layer argument in one sentence. As I said on the show, a passed SPIP means it's coming, not that it's in your Spark today, and my reading is that Spark will understand files without trying to become the thing that manages them. Scott's segue was that managing them is the catalog's job (does the file exist, and am I allowed to read it), and Iceberg has already started a [thread on access delegation for FILE](https://lists.apache.org/thread/s283f6obyqf6c14bn37sw7vtf9y1c9mj) in the REST catalog for exactly that.

I also talked about language-agnostic UDFs as if the vote had just passed, and the correction is that the [Unified UDF Execution Protocol SPIP](https://lists.apache.org/thread/czlg2bbh3hc22810qdcptg04hzrtv424) from Haiyang Sun passed back in March. The point stands, though. Spark Connect lets you write queries from Go, Rust, Swift or TypeScript, but UDFs only really work in Scala, Java and Python, through mechanisms that don't generalize; the SPIP defines one IPC protocol for UDF workers that run outside the executor, plus a worker specification for how those workers are installed, started, connected and torn down, so a client language brings its own worker instead of Spark implementing every runtime (which sounds like a huge pain in the ass). Spark 4 already moved Python UDFs toward Arrow batches, and this is the same decoupling pushed further. I'm noticing people use Spark more and more to route workloads rather than purely execute them, and Scott's point was that this is the value of Spark as a shared vocabulary; even if the backend changes, it's still a Spark application.

## Iceberg 1.12 and the other half of the week

The [1.12.0 RC0 vote](https://lists.apache.org/thread/7qtxrysl1w5sjs7o74y31snt0jrkf5qb) went out from Neelesh Salian just before we recorded. It didn't pass (a fix landed and RC1 followed), and [1.12.0 shipped on September 30](https://github.com/apache/iceberg/releases/tag/apache-iceberg-1.12.0). A correction on the size: Scott remembered over 230 pull requests, but the release notes list 765, which makes his "consolidation release" framing even more apt. Much of it is v4 groundwork (a v4 manifest reader, relative paths, content stats); Scott's summary was that you can technically set a table to v4 and it won't do anything useful yet, and nothing in the notes suggests it's ready for production. The part that connects to Spark is that 1.12 baselined a [formal expression spec](https://github.com/apache/iceberg/pull/16652), with the REST spec updated to match; Scott compared it to protobuf, where you write the definition once and compile it down for each language, instead of keeping fifteen copies of the same thing.

There's also a [thread on the `_pos` column](https://lists.apache.org/thread/sx4tndlb4vkcpj2yq9cob7fhddzd701x) in the efficient column updates proposal, which is about not rewriting a whole data file to change one column in one row. Scott's history of deletes got muddled on the show, so to set it straight from the [spec](https://iceberg.apache.org/spec/): v2 allowed position and equality delete files, v3 forbids new position delete files and replaces them with deletion vectors, and v4 forbids new equality deletes ([that spec wording](https://lists.apache.org/thread/2pgfvf8v5ob221q5t2xwzjo4xvw5ltz1) went to a vote the following week).

The other half of the week ran in the opposite direction. The [iceberg-datafusion integration is moving](https://lists.apache.org/thread/pk4yqd4llr85lmq3gskbfl9v31sfqpp9) out of iceberg-rust into `apache/datafusion-iceberg`, approved on both the [DataFusion](https://lists.apache.org/thread/6k5lws31c61y1lx2s34pxo4lmc7334lr) and [Iceberg](https://lists.apache.org/thread/ytb9x7x8ff3b7031kcrc05nzjtmh091s) lists. Scott called it a happy divorce, and the reasons in the thread fit the thesis: iceberg-rust wants to stay engine-agnostic, its integration pull requests were going stale, and projects like Comet couldn't upgrade DataFusion or Arrow until iceberg-rust did. Keeping the shared layer neutral means moving engine-specific code out to the people who use it.

## Catalogs and releases

Lakekeeper (an Iceberg REST catalog written in Rust) shipped [0.13.4](https://github.com/lakekeeper/lakekeeper/releases/tag/v0.13.4), adding AWS partition support in S3 policies, and [0.13.5](https://github.com/lakekeeper/lakekeeper/releases/tag/v0.13.5), adding S3 request signing for generic tables. Generic tables are Lakekeeper's way of cataloging non-Iceberg tables (the [Generic Table API arrived in 0.13.0](https://github.com/lakekeeper/lakekeeper/releases/tag/v0.13.0) with Lance), which is what Scott meant by it becoming multimodal. Unity Catalog's open source project got full Iceberg REST catalog table operations on main, so any Iceberg REST engine can create, write, read, rename and drop Iceberg tables in it; we said 0.7 would land around the first of October, and [0.7.0 actually shipped on October 13](https://github.com/unitycatalog/unitycatalog/releases/tag/v0.7.0).

Congratulations, too, to [Polars 1.44.2](https://github.com/pola-rs/polars/releases/tag/py-1.44.2), [Lance 12.0.0](https://github.com/lance-format/lance/releases/tag/v12.0.0), Parquet Format 2.14.0, Lakekeeper and [Airflow 3.3.2](https://github.com/apache/airflow/releases/tag/3.3.2) for shipping that week.

## So, about the types

When I asked Scott what trend he saw in all of this, he said interoperability, consolidation and simplicity, with Parquet as the substrate under every table format and Connect as the way of declaring what you want independent of what runs it. I'd put it a little more narrowly. The week I called quiet unless you like types was full of projects deciding what a type means once, for everyone: a FILE that Parquet, Spark and an Iceberg catalog all agree on, a version number a reader can trust, a UDF protocol any client language can implement, and an expression spec that compiles down instead of being copied. The features will come in the releases after; this was the part that decides whether they work across engines when they get there.

This is my write-up of the first episode of This Week in Open Lakehouse, the weekly show Scott Haines and I host on open source data engineering news; the video is above, and the audio, show notes and full transcript are further down this page.

I opened the first episode by forgetting the name of the show, which is a strong start for something you intend to do every week; Scott floated a new name every episode, I brought up Adam Savage's podcast that never settled on a title and became Still Untitled, and we agreed the working title was fine for now. The point of the show is that keeping up is hard unless you live on the dev lists, and even the contributors I know live on one; by the end of the hour the thing I said out loud was that I hadn't appreciated how interconnected the ecosystem is until we read it all in one sitting, every project coevolving in parallel with the ones beneath and beside it.

**That was the real story of the week: the formats, engines and clients were all making room for the same new kinds of data at once (nanosecond timestamps, files, vectors), which moves the hard work to the seams between projects, meaning who maintains the integration code, how a reader treats bytes it doesn't understand, and how far one project's major versions ripple downstream; the best decision of the week, moving the Iceberg integration for DataFusion into DataFusion itself, was two communities putting a seam where the people who break it can also fix it.**

## Parquet 2.14, and the 96 bits it took to get to nanoseconds

On the show I said Parquet 2.14 had either shipped or was about to, and that I didn't know whether the vote had wrapped; it had, on September 11, a week before we recorded. The [release](https://github.com/apache/parquet-format/releases/tag/apache-parquet-format-2.14.0) carries chronological ordering for INT96 timestamps, the new FILE logical type, the ALP floating point encoding (marked as preview) and a round of fixes to errors and inconsistencies in the Variant documentation. The episode title promised nanosecond precision, which is a separate change; the [vote to let the timestamp logical type annotate a 12-byte fixed-length column](https://lists.apache.org/thread/v11pw7sbnkdxzjhkmcbsx06clyvjv0xx) passed the same day, so nanosecond timestamps are approved for the format but not in 2.14.0.

I asked Scott what nanosecond precision is actually for, and his answer was collisions; at high enough event throughput, plenty of events share a millisecond, and the old workaround was to split a timestamp across columns (he reached for Protobuf, whose timestamp is seconds plus nanos). His other point was the one that explains the proposal's design, which is that systems without proper nanosecond support either drop precision or roll over, so a cast from a long gives you a timestamp in the year 2200-something, a "time traveling timestamp." That number isn't random. A signed 64-bit count of nanoseconds runs out about 292 years either side of 1970, in 2262, which is why the [original proposal](https://lists.apache.org/thread/l41qxghl5wwtt58m40gxk34gjnqz7jjd) says plainly that Parquet's INT64 timestamps can't cover the full SQL range of years 0001 to 9999 at nanosecond precision, and asks for 96 bits instead. Spark's own [nanosecond SPIP](https://issues.apache.org/jira/browse/SPARK-56822), which I called an active proposal on the show and which was in fact already accepted and being implemented, solves the same problem in memory with a 64-bit count of microseconds plus a 16-bit nanos-within-the-micro field; the format and the engine arrived at different layouts for the same range, which is exactly the kind of seam someone has to write a converter for (vectorized Parquet reads for the new types landed as one of its sub-tasks).

My own take was the AI one, offered with the caveat that I didn't want to shove AI into every story; a lot of new models are about spatial ability (robotics, self-driving), and their data arrives on the infrastructure we already run. Scott agreed, while noting that most people will never need nanoseconds; I think that's right, and it's why the format work matters now, before the people who do need it each invent their own encoding.

The Variant doc fixes matter more than docs usually do, because Variant had many interpretations before it went into Parquet, and one source of truth for the binary representation is what lets Spark, Flink and everyone else implement it once (Scott is preparing a talk on Variant shredding for old banking systems that still speak XML, which is a more honest test than yet another JSON demo).

Under all of this, and not something we got to on air, Ryan Blue opened a discussion on [how readers should behave with a file written in an unsupported format version](https://lists.apache.org/thread/7ghf93l0ss74l3k4jo9qc2bdmrmng3hm) and [argued that they should fail](https://lists.apache.org/thread/clk5247h8gowxvo9wjoyncfdyoobzqrp), since a promise that every reader ever written will either read a future version correctly or fail is one nobody can keep; new types are only safe to add if old readers know what to do with them.

## Files, vectors and credentials: Spark catches up to its formats

Scott's framing, which I think is correct, was that you can work backwards through the week: Lance built the momentum around multimodal data, Parquet now has a FILE type, and Spark is now voting on its own. The [FileType SPIP](https://lists.apache.org/thread/ycgvv34l0b678gzkcc4hj0oskhqkdpjv) (spelled FILE in SQL) [passed on September 14](https://lists.apache.org/thread/jgh4t8fp64vt1so8m7xv5wf103wyrx9m), and it comes from Burak Yavuz, who also wrote the [Parquet FILE logical type](https://github.com/apache/parquet-format/releases/tag/apache-parquet-format-2.14.0), so the convergence I described on the show is the same person on both sides of the seam. A FILE value holds a file's path plus a little metadata, not its bytes; per [SPARK-59132](https://issues.apache.org/jira/browse/SPARK-59132), a query can filter, join and project PDFs, images, audio and video without reading them, instead of stuffing bytes into a binary column or keeping a path string and hoping downstream code knows what it means. Scott contrasted it with Spark's older image support, built around one image at a time, whereas a file with a known media type lets you say "this is a video, extract its frames, and distribute that work."

The [VECTOR SPIP](https://issues.apache.org/jira/browse/SPARK-58787) is the one that is genuinely still open. It proposes a fixed-dimension numeric type (`VECTOR(768, FLOAT)` is a different type from `VECTOR(1536, FLOAT)`), with syntax following the emerging SQL standard proposal, and it's careful to call itself a new logical type and schema contract rather than a new in-memory layout, since execution reuses Spark's array representation. That is the part I find persuasive: today an embedding column is an array (or worse, a blob) the planner knows nothing about, and naming the type is what lets the engine reason about it. Scott's version was that the Spark ecosystem always does this; people support vectors through extensions, best practices emerge, and then they roll back into the project, the way AUTO CDC did for change data capture.

[OIDC credential propagation](https://issues.apache.org/jira/browse/SPARK-57703) needs a correction, and a slightly bigger one. I described it as catalogs getting identity-aware credentials through Spark, and Scott talked about Spark connecting to the catalog the same way everywhere; the SPIP is narrower. It's about Spark on Kubernetes carrying an OIDC token from the driver to the executors and turning it into per-workload credentials for cloud storage (S3, ADLS, GCS, MinIO and the like), and it lists catalog and Hive Metastore OIDC integration as future work, explicitly out of scope. It was also already accepted rather than open, and it was pulled from the 4.3 branch to land in 4.4.0. Scott's history lesson is the right context, though: on HDFS, Kerberos made sure Scott could only read Scott's files, and the SPIP calls itself the Kubernetes-plus-OIDC equivalent of Kerberos and delegation tokens, replacing one cluster per user or one over-privileged service account. Governance is incredibly boring for the user, as I said on the show, and it's what makes the rest usable.

## Who maintains the glue: iceberg-datafusion moves house

The governance story of the week was where Iceberg's DataFusion integration should live. Matt Butrovich [opened the discussion](https://lists.apache.org/thread/53lqjw7371myww42l19vx923cjzrgg68) on both dev lists at once: the table provider made DataFusion a dependency of iceberg-rust, pull requests against it went stale because few iceberg-rust committers use it, and projects depending on both (Comet, the Spark accelerator built on DataFusion) couldn't upgrade until iceberg-rust upgraded its DataFusion and Arrow versions first. Andrew Lamb, DataFusion's PMC chair, [added](https://lists.apache.org/thread/2pvkhcspjrljrtmzp7r3nfdvr4soq5bs) that at VLDB he'd spoken to several companies adding Iceberg support to their products, and all of them had forked iceberg-rust. He proposed a new repository, `apache/datafusion-iceberg`, with a vote in each community; the [Iceberg vote](https://lists.apache.org/thread/ytb9x7x8ff3b7031kcrc05nzjtmh091s) passed on September 14 and the [DataFusion vote](https://lists.apache.org/thread/8x3l4m4gzhy2gvd9ppfqhxfl9tlxrqw6) on September 16, both unanimously, so by the time we recorded it was decided rather than pending.

Scott's read was that DataFusion is essentially the Spark of the Rust world, a large dependency many iceberg-rust users don't need, so iceberg-rust should focus on protocol compatibility rather than compiling and testing against an engine it doesn't own; and every fork is harder to bring back to mainline, which is the Spark story too. Mine was that Spark and Airflow are pushing release velocity hard right now, and an integration coupled to another project's release, reviewed by people without deep expertise in that engine, slows both down; here the engine is the one that changes fastest.

DataFusion [55.1.0 passed its vote](https://lists.apache.org/thread/rqq866ndtwoq0vl1z1wbh6sfwj6dm483) on September 11 (we described it as still in voting), and Scott brought up [ZeroVer](https://0ver.org/), the joke-but-real convention of never leaving 0.x, as something he'd heard discussed in the Delta Rust community. He suggested DataFusion's big numbers mean its majors aren't really breaking, and I have to correct that; DataFusion follows semver, and its docs carry an [upgrade guide for each major version](https://datafusion.apache.org/library-user-guide/upgrading/index.html) precisely because they do include breaking API changes. That's the mechanism behind the whole move. When the engine underneath you ships breaking majors on a regular cadence, the integration has to be updated by someone who understands the breaks; [hudi-rs 0.5.0](https://lists.apache.org/thread/3z8nykp8k8nqlp488bzr1n0oxbwhzhfo), released the same week, jumped from DataFusion 46 to 54 in a single release, which tells you how far a downstream project can drift when the glue isn't anyone's main job.

## The Rust shelf fills up

The [Spark Connect Rust client 4.2.0](https://lists.apache.org/thread/o9h87grjcot5foczfnz444qph2gg7w5q) is another correction: I said it had just had its release candidate added, and in fact RC2 [passed on September 7](https://lists.apache.org/thread/lxjdg2f2drrz8hz29g7fgmc4t02rfmp2). It's also more than a Rust client: it's a ground-up Rust rewrite of the PySpark Connect client, published as `pyspark-client-rust` as a drop-in replacement for `pyspark-client`, alongside the full Rust API (Rust UDFs included) and a native transport instead of grpcio or py4j. Scott's case for Connect was escaping jar hell, since a client that only speaks the protocol doesn't drag the cluster's dependencies into your application; I'd add one nuance to his "any version of Spark," which is that the client's version deliberately tracks the Spark release it targets. My own interest is what a Rust-native client means for other Rust engines (Polars, say) that could embed it and talk to a Spark cluster directly, with results coming back as Arrow IPC that any engine can read.

[Polars 2.0.0 rc.1](https://github.com/pola-rs/polars/releases/tag/py-2.0.0-rc.1) makes the streaming engine the default for SQL, listed as a breaking change, and it also reuses native metadata for Iceberg sinks, which as I understood it cuts round trips to the catalog. Scott pitched it as an agent story, a streaming dataframe running in the small container an agent spins up on demand instead of a cluster sized for petabytes; to me it's the same blurring of batch and streaming Spark went through with micro-batch, real-time mode and declarative pipelines.

[Lance v12.0.0](https://github.com/lance-format/lance/releases/tag/v12.0.0) shipped on September 17, the day before we recorded, after the run of betas we'd been reading. Scott found the versioning confusing, fairly; v12 is the library's version, and the change that matters is that the stable file format was resolved to 2.2. The two features I picked out were segment-based distributed vector search in the Java client, which matters for Spark and Flink users, and the in-memory write-ahead log work, which reads like groundwork for multi-writer concurrency and very large workloads. I also said on the show that Lance's creators also created pandas and asked not to be quoted on it; the accurate version is that LanceDB co-founder Chang She was one of the original co-authors of pandas, and Scott was right that [Midjourney was an early customer](https://techcrunch.com/2024/05/15/lancedb-which-counts-midjourney-as-a-customer-is-building-databases-for-multimodal-ai).

Two footnotes I hedged on air: Arrow's [vote to informally deprecate Tensor and SparseTensor in IPC](https://lists.apache.org/thread/6w7o59hqp2vydc2ksy23m8pk9czlgw06) [passed](https://lists.apache.org/thread/w7nvhjyks3p3smw5kq4ylv0nkwxq2s2q) on September 8, and hudi-rs 0.5.0, which I described as mid-vote, was [released](https://lists.apache.org/thread/3z8nykp8k8nqlp488bzr1n0oxbwhzhfo) on September 10. Scott then segued into ZSTD becoming the default Parquet codec, and one correction there: this is Hudi's default, not Parquet's. The [Hudi discussion](https://github.com/apache/hudi/discussions/19615) proposed ZSTD in place of GZIP for the native Parquet log files merge-on-read tables now write, since those files get rewritten at compaction anyway and GZIP's CPU cost lands on the write path; the maintainers aligned on it and asked for a PR.

## Governance, which we promised to make exciting

The Iceberg REST catalog had its big week earlier in the month. Prashant Singh's [finer-grained read restrictions](https://lists.apache.org/thread/nwnmyjs2phrpmxtb04p6vlwml6kywm83) passed on September 3, and Andrei Tserakhau's [catalog-provided labels on LoadTableResult and LoadViewResult](https://lists.apache.org/thread/od2qyt4b5yz3tobgfv10hgz3h79m6t4g) on September 8 (read-only, flat key-value labels for now). Scott walked through the mechanism: a trusted engine asks the catalog to load a table and gets back, along with the metadata, instructions for how to mask columns and which row filters to apply, so the same policy holds whether the query comes from Spark, Trino or something else. With Lakekeeper, Polaris, Unity Catalog and Gravitino all in the picture, his point was that governance which only works inside one catalog doesn't survive contact with an enterprise. Scott said Iceberg 1.12 was in final review; the [RC0 vote](https://lists.apache.org/thread/7qtxrysl1w5sjs7o74y31snt0jrkf5qb) opened the day we recorded and the release was [announced](https://lists.apache.org/thread/kst8b58yjnvfy353g2ysvb4fkx3xdcr9) on October 1.

## And then we talked about agents

[MLflow 3.16.0](https://github.com/mlflow/mlflow/releases/tag/v3.16.0) (released September 4, so not quite "this week") lets you describe a trace view in plain English and has the MLflow Assistant build it. On Omnigent, Scott highlighted the [live GitHub PR panel](https://github.com/omnigent-ai/omnigent/releases/tag/v0.13.0) from 0.13 (0.14 was already out by the time we recorded). I came at it from a Reddit thread asking whether anyone still pair programs (the consensus was no, everyone is alone in their own agent's terminal); a shared session, where Scott drives with his harness and I'm in mine with shared history and MCP servers, is the closest thing to pairing I've had in a while, and Scott added that it also means nobody on a team pays to rebuild the same context.

## Still untitled

We ended a show that was meant to be seven minutes at well over an hour, then went back to video games, which I asked the editing team to cut. The name is still a working title. But the thing I said at the end holds up better on paper than it did live: none of this week's news happened in one project. Parquet defined a FILE type and Spark voted in its own a few days later, from the same author; Parquet approved 96-bit nanoseconds while Spark implements an 80-bit layout of its own; the REST catalog standardized masking so every engine applies it the same way; and the integration code that kept breaking moved to the community that ships the breaking changes. The interconnectedness is the work now, and the projects doing it well are the ones deciding, deliberately, who owns each seam.

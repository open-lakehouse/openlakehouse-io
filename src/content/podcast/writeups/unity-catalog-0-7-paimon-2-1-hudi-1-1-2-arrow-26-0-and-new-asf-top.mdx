This is my write-up of episode 6 of This Week in Open Lakehouse, the weekly show Scott Haines and I host on open source data engineering news; the video is above, and the audio, show notes and full transcript are further down this page. We skipped a week because Scott had the flu, and came back in week 42 of the year, which Scott treats as a holiday on account of The Hitchhiker's Guide to the Galaxy (I'm a big fan of the book, less of a fan of the passage of time against my will).

Partway through the episode I admitted something that I think is the most honest thing either of us said: this was a hard week to find the thread in. For a while the thread had been easy; every format was converging on the same type system, and every execution engine seemed to be growing a Rust accelerator underneath it. This week's releases were health endpoints, backports, compatibility checks and reliability fixes, the kind where you go looking for the headline feature and find a changelog of things that used to break and now don't. I called it an era of hygiene releases on the show, and the longer I sit with it the more I think that's the actual story rather than the absence of one.

**The thread of this week is that the releases were mostly hygiene rather than headline features (probes and multi-instance support in a catalog, a patch line revived after ten months, a table format refusing to write metadata that would mislead an Iceberg reader), because agents have made writing code cheap enough that the scarce things in open source are now review, CI capacity and trust, and an Apache top-level project is the foundation's formal statement that a community has enough of all three.**

## Unity Catalog 0.7 (Iceberg tables, plus the boring parts that make a catalog runnable)

Unity Catalog 0.7.0 [shipped on October 13](https://github.com/unitycatalog/unitycatalog/releases/tag/v0.7.0) after a last round of stability fixes, with the Docker image a day later (Scott builds it behind a proxy as a supply chain precaution, which is less fun on hotel Wi-Fi). The headline is the one people have been asking about for a long time: Iceberg tables in Unity Catalog through the Iceberg REST catalog APIs, so any engine that speaks the protocol can create, write, read, rename and drop Iceberg tables in UC, Spark included, without a UC connector. Native Iceberg tables are on by default, a behavior change worth reading about before you upgrade.

What I find more telling is everything around the headline. The server can now serve `/livez`, `/readyz` and a Prometheus `/metrics` endpoint on a dedicated port for Kubernetes probes; authorization changes made on one instance propagate to the others, with a single bounded database connection pool, so you can run a pool of servers behind a load balancer and stop treating the catalog as a single point of failure. Scott's framing was that when the catalog is down your data is down, which is why these features decide whether anyone runs it in production. One precision on our summary: both of the operational features are opt-in, since the probes only appear when you start the server with `--obs-port`, and cross-instance policy refresh needs `server.authorization.policy-refresh=true`.

The Spark connector is published for Spark 4.0, 4.1 and 4.2 on Scala 2.13, with a caveat Scott flagged and I'd underline: you can't use Iceberg with Spark 4.2 yet, because Iceberg itself hasn't shipped a Spark 4.2 runtime. The Iceberg community [merged the Spark 4.2 source but excluded it from both the binary and source tarballs](https://lists.apache.org/thread/kdxjm9kbn33m2084y6wo1psprn63j4rr) of [1.12.0](https://github.com/apache/iceberg/releases/tag/apache-iceberg-1.12.0), which is the "almost made it" Scott mentioned. If you want to try it without assembling a lab from spare parts, the [Unity Catalog playground](https://github.com/open-lakehouse/unitycatalog-playground) in the Open Lakehouse GitHub organization bundles UC, Spark, Delta Lake and marimo notebooks, including the native Iceberg path.

## Paimon 2.1, and a table format that would rather refuse than mislead

Apache Paimon 2.1.0 and PyPaimon 2.1.0 [passed their release vote on October 12](https://lists.apache.org/thread/jogdh2gokbhsly81hp9od28hvfrr8kzw), two months after [2.0.0](https://github.com/apache/paimon/releases/tag/release-2.0.0). I called it a quality-of-life release on the show with the caveat that I could be wrong, since I'm not a heavy Paimon user; it's far bigger in the stacks run by companies like Alibaba, ByteDance and Tencent, which operate at enormous scale and often still on Hive Metastore and Hadoop. Reading the [release notes](https://github.com/apache/paimon/releases/tag/release-2.1.0) properly, it's a multimodal release as much as a cleanup one: native Rust scan planning from Python, Arrow writes and an Arrow batch reader for multimodal scans, variant path updates and shredding, BTree global index improvements, and full-text indexes on tables with deletion vectors. Scott's addition was about where Paimon came from; it and Fluss were built to make a table format cheap to upsert into, keeping correct state without the pile of failure points a typical streaming stack accumulates, and the [README](https://github.com/apache/paimon) confirms the mechanism he was reaching for, which is an LSM-based layout for primary-key tables.

The part I wanted to highlight is Paimon's Iceberg compatibility, because it's a hygiene story in the most literal sense. Paimon can mirror its tables as Iceberg metadata, and this release is full of changes that make the mirror stricter rather than broader. One correction to what I said on the show, though: I described the nanosecond timestamp rule as Paimon waiting until Iceberg can represent nanoseconds, and that isn't quite it, since Iceberg's v3 spec already has `timestamp_ns`. The actual problem, per the [pull request](https://github.com/apache/paimon/pull/9455), is that Paimon writes high-precision timestamps as Parquet INT96, which Iceberg reads as a microsecond timestamp, so the metadata and the data files would disagree and an Iceberg reader would silently return wrong values; Paimon now refuses such a column whenever Iceberg metadata is enabled, and tells you to lower the precision or turn the mirror off. Variant runs the other way: Paimon used to reject variant columns in the mirror for every format version, and with row lineage now emitted for Iceberg format version 3, it [allows publishing variant columns on v3](https://github.com/apache/paimon/pull/9246) and keeps rejecting them on v2, where the type doesn't exist. Neither change adds a capability you'd put on a slide; both remove a way for two engines to disagree about the same table without telling anyone.

## The patch releases (Hudi, Kafka, and the end of Arrow 26)

Hudi is the clearest example of the week's shape. [Apache Hudi 1.1.2](https://lists.apache.org/thread/3rcz9j3hl9bofbv81dgzcnb09m8r2h9r) arrived roughly ten months after 1.1.1, on a release line that's no longer the newest (Hudi had already shipped [1.2.1](https://github.com/apache/hudi/releases/tag/release-1.2.1) in September), and it consists of 19 backported pull requests. The [release notes](https://hudi.apache.org/releases/release-1.1) are mostly about Flink: instant ordering for Flink upserts with CDC, including on merge-on-read tables, and data-loss fixes in the Flink write path during global failover. Scott's TLDR was the right one; if you run Hudi with Flink, upgrade, because the alternative is a chance of losing writes.

I also co-opted the streaming segment for Kafka, and owe a correction there. I described [Kafka 4.2.2](https://lists.apache.org/thread/4k6z9lzbkt11hz527nk8ff08mp3m29gt) as a minor release made mostly of performance enhancements; it's a patch release, which the [announcement](https://kafka.apache.org/blog/2026/09/29/apache-kafka-4.2.2-release-announcement/) calls "a bugfix release that includes several critical fixes", and it came out on September 29, so it's older news than we made it sound.

Arrow is the coda to something we covered last time while the vote was still open. We guessed the 26.0.0 vote would pass and it did; the release is [announced](https://lists.apache.org/thread/mv2hs6tofm5ynoc7dx5y36sf8nqh31hd) with 337 resolved issues since 25.0.1. Scott also congratulated Jeffrey Vo on joining the Arrow PMC, which is well deserved, but one correction to the timing: he called it last week's news, and the [announcement](https://lists.apache.org/thread/v55trpp9zcpl1hfwq7qr3c3nf19lmg4s) went out on August 3.

## The agent tooling corner: MLflow and Omnigent

[MLflow 3.17.1](https://github.com/mlflow/mlflow/releases/tag/v3.17.1) (October 13) is a patch release whose features are `make_judge()` support for the Decision API, a `review_queues` module for managing review queues that only works on Databricks (Scott noted, fairly, that we talk a lot about open source on this show and that one isn't), and a fix so Claude Code OpenTelemetry traces render correctly in the MLflow UI. [3.17.2](https://github.com/mlflow/mlflow/releases/tag/v3.17.2) records dataset, scorer and agent lineage on `mlflow.genai.evaluate` runs.

[Omnigent 0.18.0](https://github.com/omnigent-ai/omnigent/releases/tag/v0.18.0) (October 13) is the meta-harness that sits on top of Claude Code, Codex, Pi, Cursor and the rest, and I run my own Omnigent server, so I'm not neutral. The release lets you install custom agents with `omnigent agent add` and manage them with `list` and `remove`, so an installed agent appears in the new-session picker on every host; the [changelog](https://github.com/omnigent-ai/omnigent/blob/main/CHANGELOG.md) also has `omnigent agent add owner/repo` for installing the agents in a GitHub repository, which is something Scott and I should probably use to share ours. A new `web_read` builtin fetches a URL as clean markdown through Jina, Nimble or Firecrawl, and the session panel now shows GitLab merge requests and Azure DevOps pull requests alongside GitHub. I skipped the reliability fixes on the show as boring, which in a week about hygiene was the wrong call; sessions surviving host reconnects and runner handoffs are exactly the fixes Scott meant when he said early users complained about stuck sessions and he no longer finds anything to complain about. It's Apache 2.0, and [0.19.0](https://github.com/omnigent-ai/omnigent/releases/tag/v0.19.0) followed a week later.

## Who reviews all of this, and who pays for the CI

The back half of the episode left the changelog. My worry about this era was that with AI available, people would simply fork a project and vibe code the features they wanted; what I'm actually seeing is that a lot of the work comes back upstream, as broad, small fixes that pay down technical debt, which is good for the projects and hard on the people reviewing it. Twenty or thirty PRs from one person at once is overwhelming, and the reviewer's question (does this person understand the fix, and is it maintainable) gets harder as a project grows. Scott's version was that the hard part of open source has always been communication, finding a shepherd in the community willing to take your flock of PRs through the goalposts, and that the people who do that shepherding spend a large part of their lives on it.

My take is that the better route into a project is credibility first: show up, weigh in on design decisions even as a user, become a familiar face, and then contribute, rather than dropping one enormous PR and getting angry when it sits for a week. A project like Airflow is deployed by Google, Amazon, Microsoft and Astronomer as a vendor product, so a change that looks fine in isolation touches a lot of production systems. Scott pointed to [Apache Magpie](https://news.apache.org/foundation/entry/the-apache-software-foundation-announces-new-top-level-project-5), the ASF project that gives maintainers agent-assisted tools for triaging issues and pull requests, as one response to that torrent, since staleness, duplicates and issue grooming used to be done entirely by hand.

The cost nobody talks about is CI. A large project that used to get a couple dozen PRs a day may now get hundreds, and every one of them triggers a build; a full Spark build and test run, by Scott's estimate, is around twenty minutes, on machines that effectively never stop. That bill is paid by a nonprofit that procures its own resources without a hyperscaler's budget; Anthropic's [$1.5M donation to the ASF](https://news.apache.org/foundation/entry/the-apache-software-foundation-announces-1-5m-donation-from-anthropic) in April was earmarked in part for build infrastructure, which tells you where the pressure is. ASF Infrastructure has plenty of open tickets and is keen to onboard help (I plan to help more), and release managers telling them what their projects need is how they learn what to optimize.

## Three new top-level projects, by two different routes

The board established [Apache Auron](https://www.apache.org/foundation/board/minutes/Auron.html), [Apache Reqsign](https://www.apache.org/foundation/board/minutes/Reqsign.html) and [Apache ResilientDB](https://www.apache.org/foundation/board/minutes/ResilientDB.html) as top-level projects on September 16, and the foundation [announced all three on October 14](https://news.apache.org/foundation/entry/the-apache-software-foundation-announces-new-top-level-projects-7). One correction to how we framed them: we talked about all three as incubator graduations, and two of them are. Reqsign took the other route; it spent years as a subproject of Apache OpenDAL, and its initial PMC is made up entirely of former OpenDAL PMC members, so it was spun out rather than graduated.

| Project | What it is | Route to top-level |
| --- | --- | --- |
| Auron | A Rust accelerator for big data query engines, built on DataFusion | Incubator, entered August 2025 |
| Reqsign | A Rust library that signs HTTP requests to cloud services without vendor SDKs | Subproject of Apache OpenDAL |
| ResilientDB | A modular, permissioned blockchain framework on Byzantine fault-tolerant consensus | Incubator, entered October 2023 |

Auron is the one I'm most interested in. It's the project many of you know as Blaze, and it takes an optimized physical plan from Spark, maps it into DataFusion's execution plan and runs it natively in Rust, a cousin of DataFusion Comet that scopes well beyond Spark, with Flink and with Paimon, Iceberg and Hudi. The foundation's announcement says it runs about twice as fast as Spark 3.5 and saves about 50% of cluster resources, and my complaint on the show stands: if you want your accelerator to look good, 3.5 is a convenient baseline, and I'd love to see the same comparison against Spark 4.

Reqsign is the one Scott took, and it's a good example of hygiene as a product. Every object you read from cloud storage is a signed HTTP request, and the signing is usually done by a full vendor SDK that bloats whatever client carries it; Reqsign does only the signing, for AWS (SigV4 and multi-region SigV4a), Azure Storage, Google Cloud, Aliyun OSS, Huawei Cloud OBS, Oracle Cloud and Tencent COS. It's already used by OpenDAL, uv and Lance, so you've probably run it without knowing.

ResilientDB is a blockchain, and it's been a while since I've seen anything in that ecosystem that excited me outside of crypto mining. It began as a research project at UC Davis in 2018, orders transactions with PBFT and separates the ordering of transactions from their execution, so throughput stays high while the ledger stays consistent even when some nodes fail or act maliciously. My speculation, and it is only that, is that this kind of consensus becomes interesting again if agents start transacting with each other at scale; if agents do personal shopping or exchange data on our behalf, the questions of a shared source of truth, identity and auth stop being hypothetical, and I'm not sure banking systems are built for transactions of those sizes and frequencies.

## Start with a typo

Scott's parting advice was to join an open source community, because the work is increasingly agents running agents and the community is where humans still gather, and to start small: fix a typo in the docs rather than opening a nine-hundred-file PR, and find people willing to shepherd you along. I agreed, and added the part that worries me; developers seem more isolated than ever, building the same tools over and over, with less pair programming and PR threads where one person's agent posts a review and another person's agent replies (please don't go through my PR list, I'm guilty of this too).

That's also where the missing thread was. The releases this week didn't have a headline because the work that matters right now is the work that keeps a project trustworthy as code gets cheaper to produce: probes on a catalog, a patch line revived for Flink users, a format refusing to write metadata that would lie to another engine, and three communities the foundation judged able to govern themselves. Every one of those depends on people reviewing, maintaining and paying for builds, and none of them gets written by dumping a large PR on a project you've never spoken to.

This is my write-up of episode 5 of This Week in Open Lakehouse, the weekly show Scott Haines and I host on open source data engineering news. We recorded it on a Saturday from two different conferences (me at Community Over Code, the conference formerly and still informally known as ApacheCon, up very late in Scotland; Scott at Data and AI Weekend in Texas, the descendant of Data Day Texas), so the first stretch of the episode is us comparing notes on who we'd met; the video is above, and the audio, show notes and full transcript are further down this page.

The contrast between the two rooms was the fun part. Scott's conference was full of people with enormous online followings, and mine was full of committers and PMC members I only recognized by their dev list names, who don't post much anywhere and are quietly making core changes to formats and engines that the cloud providers then pick up and run everyone's data through. Before we'd even reached the first news item, Scott went off on a tangent about Unity Catalog 0.7, which had slipped from its planned date because the release candidate turned up a bug that, in his words, would have made it easy to drop an entire table; his point was that you want a catalog (Unity Catalog, Polaris, Lakekeeper, whichever) to stop you, the way you once wished something had stopped you from running `rm -rf` at the root of a Linux box. That tangent ended up being the episode.

**Nearly everything that moved this week was a project deciding which layer gets to make a promise and then enforce it (the catalog over destructive maintenance, the file format over what a vector may contain, the policy engine over a whole agent session rather than a single prompt), because once agents are the ones issuing the queries, writes and tool calls, a guarantee that lives only in a convention or in a careful human's habits is not really a guarantee at all.**

## Comet and Ballista, or Andy Grove's week

DataFusion Comet (the DataFusion-based accelerator that runs Spark's physical plans natively in Rust) [released 1.1.0](https://datafusion.apache.org/blog/2026/10/01/datafusion-comet-1.1.0); one correction up front, since our show title and I both said "1.10", and the version is one point one point zero. The [changelog](https://github.com/apache/datafusion-comet/blob/992c806a7e38c2e88bd018aa5774164b0850e1fa/docs/source/changelog/1.1.0.md) credits 147 merged PRs to Andy Grove alone, which is why Scott and I spent a while asking where any of us would be without him (we need to get him on the show). Since we recorded, Andy has [proposed making Comet its own top-level Apache project](https://lists.apache.org/thread/0szsfkrog2jjr2x92zl78201zh131qzq), and the DataFusion community [voted in favor](https://lists.apache.org/thread/5mpcspj7t5kwht3yqmpmzd3j2xnp1b9l), with the board resolution still to come.

The headline is native Iceberg writes. Comet splits an eligible Iceberg write into an `IcebergWrite` operator, where executors write data files with iceberg-rust, and an `IcebergCommit` operator, where the driver makes the single commit with iceberg-java (which recomputes each file's metrics first). It's experimental and off by default, and the release notes are honest that Rust-written files won't be byte-identical to JVM-written ones (different split points, dictionary pages kept for high-cardinality columns); I pinned that caveat on Ballista during the show, but it belongs to Comet. Native Parquet writes on Spark 4.0 and later are also experimental, and there's a native shuffle path for Apache Celeborn, though released Celeborn 0.6 and 0.7 clients fall back to ordinary shuffle unless you set Comet's own Celeborn shuffle manager. That Celeborn path caught my attention because a Spark PMC member's talk at Community Over Code that week described OpenAI running Comet with Celeborn, so it isn't a toy. The rest is the low-level work you'd expect from an accelerator (not one for the weak-willed): native memory counted and logged per executor so you can see what has to fit in `spark.executor.memoryOverhead`, `map_sort` up to 18x faster on single-entry maps in microbenchmarks, and per-location S3 credentials. One correction to Scott's history of Comet, which he admitted he didn't fully know: the JVM side calls the Rust side through [JNI and the Arrow C Data Interface](https://datafusion.apache.org/comet/contributor-guide/plugin_overview.html), not Java 25's foreign function API.

[Ballista 55.0.0](https://datafusion.apache.org/blog/2026/10/03/datafusion-ballista-55.0.0), DataFusion's own distributed engine, turns adaptive query execution on by default; the scheduler replans between stages using statistics from completed work, so join decisions use real row counts, and all 99 TPC-DS queries complete and match single-process DataFusion in the project's AQE suite. The default broadcast join threshold went from 10 MB to 128 MB (I said 120 on the show), and executors now default to a bounded `FairSpillPool` sized to 70% of host or container memory, so spillable operators go to disk under pressure instead of taking the executor down. The release post's TPC-H comparison is worth a look with its caveats attached:

| TPC-H SF1000, Parquet on S3, 32 executors | Total time |
| --- | --- |
| Spark 4.1.3 | 898.2 s |
| Ballista 55.0.0 | 502.4 s |
| Spark with Comet 1.1.0 | 455.1 s |

The authors say it wasn't tuned (Spark and Comet ran 16 tasks per executor against Ballista's 8, and Comet got an extra 32 GiB of off-heap memory), so I read it as the two Rust paths landing in the same neighborhood rather than as a ranking.

We earned a correction of our own here. I said that AQE in Spark is something you enable manually; it has been [on by default since Spark 3.2.0](https://spark.apache.org/docs/latest/sql-performance-tuning.html). And Scott tied 128 MB to the usual target file size on object storage, which is a coincidence rather than the reason; the broadcast threshold is the largest join side the planner will copy to every executor instead of shuffling both sides, so raising it trades executor memory for fewer shuffles (Spark's own threshold still defaults to 10 MB). His broader point holds, that AQE earns its keep on big lookback and pivot jobs that otherwise die of out-of-memory errors and does very little for a job that is simply I/O bound.

## Unity Catalog 0.7, Delta 4.4.1, and the catalog as bouncer

[Unity Catalog 0.7.0](https://github.com/unitycatalog/unitycatalog/releases/tag/v0.7.0) shipped on October 13, the Monday after we recorded, with the feature Scott says people ask him about most: native Iceberg tables. Any engine that speaks the Iceberg REST protocol can now create, write, read, rename and drop Iceberg tables in Unity Catalog, and it's on by default. Previously the Iceberg path went through Delta, with UniForm generating Iceberg metadata for the Parquet Delta wrote; UniForm stays, but an Iceberg table no longer has to pass through Delta to live in the catalog. The production-readiness pieces are `/livez`, `/readyz` and Prometheus `/metrics` endpoints for Kubernetes (only when you start the server with `--obs-port`), faster table listing on large schemas, and managed storage cleanup, where dropping a managed table finally reclaims its files after a delay. Scott also said the next release is planned to bring an experimental console and STS support for on-prem object stores like Ceph.

I asked Scott whether this means you should stop running UniForm, and his answer was that it's an option, not a verdict. Plenty of companies run both formats, often Delta for streaming ingestion (Iceberg V3 still isn't great at frequent streaming commits) and Iceberg downstream, and both are mature, specified formats, so the choice comes down to taste and the catalog no longer makes you settle.

[Delta Lake 4.4.1](https://github.com/delta-io/delta/releases/tag/v4.4.1) is the same instinct from the format's side. On catalog-managed tables, where the catalog is supposed to control destructive maintenance, Delta now rejects metadata cleanup, column mapping removal and manual symlink manifest generation before touching the table, and it skips automatic log cleanup, auto compaction and automatic manifest generation so the original write can finish. One correction: Scott described those automatic operations as newly available, but they're the ones Delta now deliberately doesn't run on catalog-managed tables. His explanation of staged commits is the mechanism underneath; each writer stages its commit in isolation and the catalog ratifies it against the transaction log, which is what lets the catalog promise the table state is correct with several writers in play, and why it gets the final word on anything destructive.

## Parquet's vector type, and a decimal I have no opinions on

Parquet had two type proposals in discussion (I called them SPIPs on the show, which is Spark vocabulary; Parquet just has proposals and votes). The first was a numeric vector type, which Iceberg and every other table format wants so embeddings have a standard home. A [focused community call](https://lists.apache.org/thread/kgmgn2vmrz49thbfhv8b66lglsyd81xt) had narrowed the layout to a fixed-length byte array per vector or a LIST of numeric elements, and the live argument when we recorded was NaN and infinity. Ryan Blue's [proposed compromise](https://lists.apache.org/thread/ozk0p93660qx4bz10qn8pt0hzvw75vbj) was to stop making one type serve both camps: a `FINITE_VECTOR` with write-time guarantees for databases, table formats and vector indexes, and a separate type that allows NaN, with Steven Wu [backing](https://lists.apache.org/thread/5vj5ttfjrrwhjmq2y5lpd5w048qw5yv9) the finite one. (I garbled this on air by describing a finite vector that allows infinity, which is exactly what it doesn't.)

That's where it landed. [PR 624](https://github.com/apache/parquet-format/pull/624) adds `FINITE_VECTOR` as a contract on top of an ordinary LIST: exactly `num_elements` elements, required and finite, numeric or boolean primitives, no whole-vector statistics, and old readers simply see a list. The line I find most telling is that writers must enforce the guarantees and readers may rely on them without validating; the vote [passed](https://lists.apache.org/thread/rc4dso5jd5qqbf1b6cxcw88ld70l52l3) on November 9, and a more efficient physical layout is explicitly left for later. I still think this is the bigger change of the two, because once everything downstream depends on a type in a format this widely deployed it's nearly impossible to undo, so getting the contract right matters more than getting the bytes perfect first.

The second is an [extensible decimal floating point type](https://lists.apache.org/thread/5kp1bl2czz45wflydq2qzs3nld518lox) (IEEE 754 decimals parameterized by significant digits, so engines can store high-precision values without fixing a scale), and a [consolidated proposal](https://lists.apache.org/thread/dr555g8153xnjjg9y9yc7od288ddj9s3) now pins down semantics (equality for hashing and Bloom filters, IEEE `totalOrder` for statistics) while leaving the encoding open. I said I have no strong opinions here, which remains true. Scott does; he compared it to rational types, where you store a fraction and decide on precision later, and to the habit of clamping a `BigDecimal` before writing, which throws away precision you can't get back. The reason either matters to people who never think about them is that Parquet's statistics and pruning are arithmetic on these values, so if two engines disagree about how a NaN sorts or when two decimals are equal, min/max pruning quietly returns different answers.

## MLflow 3.17 and Omnigent 0.17 put rules around agents

[MLflow 3.17.0](https://github.com/mlflow/mlflow/releases/tag/v3.17.0) is where Scott, self-described lover of governance, got excited: typed Boolean or categorical feedback from judges and scorers, fine-grained permissions on runs, traces and versions with wildcard grants and explicit DENY, opt-in daily rollups for trace analytics, and aggregate evaluation metrics linked to the dataset that produced them. One correction: Scott described `mlflow.restore_run()` and `mlflow.restore_experiment()` as returning to an earlier save state, like table format time travel, but they [restore deleted runs and experiments](https://github.com/mlflow/mlflow/pull/25852). If you run a SQL backend, this upgrade also needs `mlflow db upgrade` with all writers stopped.

[Omnigent 0.17.0](https://github.com/omnigent-ai/omnigent/releases/tag/v0.17.0) is the meta-harness I use daily (one layer over Claude Code, Codex, Pi, Hermes and the rest, sharing policies and sandboxes, so a pull request written in one harness can be reviewed by another); we use it at Databricks, and I run my own server at home. Scott brought up that I'd started an OCaml Spark Connect client in an Omnigent session from my phone shortly before our panel, a funny thing to attempt in a language with no native Arrow or protobuf story; it now works against Spark 4 Connect servers, and I've written Iceberg tables from OCaml with it. The 0.17 highlights are OIDC sign-in from the desktop app and policies that gain period-based cost budgets and the conversation ID in their context, plus cost accounting that prices cached prompt tokens correctly.

The direction matters more than the list, and Databricks described it in its post on [contextual policies with session state](https://databricks.com/blog/contextual-policies-omnigent-using-session-state-better-govern-ai-agents): a policy that judges the running cost of a session, or a risk score that rises as an agent handles sensitive material, instead of judging each prompt alone. A lot of prompt injection is never visible in a single prompt, so the check has to see the session. Scott's addition was that enforcement has to sit where the agent can't escape it, the lesson containers learned when escapes forced everyone to harden their images. At the panel we ran in Bellevue that week, with folks from Databricks, Spice AI and AWS, we kept returning to how many small, redundant queries agents issue compared to humans and how little of that is observable today; session budgets and evaluation lineage are the first pieces of that observability, placed in layers that can act on it.

## Everything else we covered

The Iceberg community [voted](https://lists.apache.org/thread/pllz983cvffryzcwskglsr0cyo7p0gxx) to recommend a standard User-Agent format for REST clients (19 +1 votes, 10 binding): product tokens, most specific first, like `Spark/4.0.0 iceberg-spark/1.9.0 iceberg-java/1.9.0`, with the Iceberg library token required. Two corrections: IRC is the Iceberg REST Catalog, not an Iceberg Rust catalog; and Scott framed the header as a way to control who accesses your catalog, while the [proposal](https://lists.apache.org/thread/bzs62qqt9k4t9sr76pk0d36l47zwcpyb) explicitly says it's advisory, must not be used for authentication or to reject requests, and isn't capability negotiation. That makes it a useful counterexample to the rest of the week; it's a promise clients make about themselves, so the spec is careful not to let servers treat it as one they can enforce. (And no, user agent has nothing to do with AI agents, as I learned from the Mozilla docs.)

[Arrow 26.0.0](https://arrow.apache.org/blog/2026/10/08/26.0.0-release/) is housekeeping, and its most relevant change is that the Parquet reader now tolerates logical and physical type combinations it doesn't recognize instead of failing, which is what you want as types like the vector arrive. PyArrow drops Python 3.10, adds 3.15, requires NumPy 2.x and drops pandas below 2.2.2 (I said 2.0.3), and S3 support moved into its own `libarrow_s3` library. My Arrow story on the show was that the official Spark 4.2 Python images ship without PyArrow, while regular Python UDFs are Arrow-optimized by default since 4.2.0, so a plain `@udf` fails on an unmodified image. An update: the [patch I mentioned](https://github.com/apache/spark-docker/pull/138) was closed, since those images mirror Dockerfiles in the main repo, and the agreement there was that Spark falling back to a regular Python UDF when PyArrow is missing matters more. Until then, install PyArrow yourself.

[Hudi 1.2](https://hudi.apache.org/releases/release-1.2/), out since June, added a `VECTOR` type and a `hudi_vector_search()` function in Spark SQL that returns a `_hudi_distance` column; I described a recent fix on the show that I can't match to the release notes, and the accurate version is that search is currently a distributed brute-force scan, with a native ANN index planned.

Finally, Scott flagged the Iceberg vote on the adaptive metadata tree; it [passed on October 14](https://lists.apache.org/thread/gw1jf5j1l9hk369lbcz6g4rn4l06t77c) with 9 binding votes, Scott's own non-binding +1 among the rest. To be precise, the [vote](https://lists.apache.org/thread/qch7jjnwb8pm49lt3h7lqfxj82hlg8ps) was to merge the baseline V4 AMT spec so other V4 work can build on it, and the thread says explicitly that it isn't a vote for adoption. Scott's hope, which I share, is that it makes streaming feel native in Iceberg V4.

## The release candidate did its job

My closing thought on the show was that the data and AI stacks, which have mostly run in parallel, are being joined by small pieces of low-level glue (policy enforcement, credential management, ad hoc queries, interfaces), and this week made that concrete: Delta refusing destructive maintenance the catalog didn't sanction, Parquet putting a vector's finiteness into the format so an index never has to check, MLflow and Omnigent putting DENY rules and session budgets where agents can't route around them. I keep coming back to Scott's tangent, because it's the same story at the smallest scale; Unity Catalog 0.7 was late because the release process caught a way to drop a table before it shipped. The people writing these guarantees are mostly the unassuming dev list names I spent the week putting faces to, and their work matters more each week because the next thing knocking on the catalog's door is less and less likely to be a careful human.

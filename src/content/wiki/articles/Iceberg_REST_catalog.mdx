The **Iceberg REST catalog** is an OpenAPI specification, maintained in the [Apache Iceberg](/wiki/Apache_Iceberg) project, that defines an HTTP interface between Iceberg clients and a catalog service. It standardizes how an engine lists namespaces, loads and commits tables and views, and obtains access to the underlying storage, so that any engine with an Iceberg REST client can use any catalog that implements the specification.[^spec] In an [open lakehouse](/wiki/Open_lakehouse), it is the common protocol that separates the choice of [data catalog](/wiki/Data_catalog) from the choice of query engine.

## History

Apache Iceberg 0.14.0, released on 16 July 2022, added a common REST catalog client that uses change-based commits so that commit conflicts are resolved on the service side.[^releases]

The specification is a file named `rest-catalog-open-api.yaml` in the `open-api/` directory of the Iceberg repository. It is licensed under the Apache License 2.0, and its `info` block describes it as the specification for the first version of the REST Catalog API, with all routes under the `/v1/` path.[^spec]

## What the specification standardizes

The specification groups its routes into several areas:[^spec]
- **Configuration.** Clients call `GET /v1/config` first. The server returns default and override properties that configure the client, and an optional list of the endpoints it supports.
- **Namespaces.** Routes to list, create, load, check and drop namespaces and to update their properties.
- **Tables.** Routes to list, create, load, check, drop, rename, register and unregister tables, and to report metrics.
- **Commits.** A table commit has two parts: requirements, which the server checks before applying changes (for example `assert-ref-snapshot-id`), and updates to the table metadata. Servers must reject unknown requirements or updates with a 400 status code. A separate transactions route commits updates to several tables atomically.
- **Views.** Routes to list, create, load, replace, drop and rename views.
- **Server-side scan planning.** Routes through which a client can ask the catalog to plan a table scan.

Each route after `/v1/` takes an optional `{prefix}` path segment, which a server can use for its own hierarchy, such as one catalog per prefix.[^spec][^glue]

The `/v1/oauth/tokens` endpoint in the specification is deprecated. The specification says that it has been deprecated since Iceberg (Java) 1.6.0, that it will be removed in Iceberg (Java) 2.0, and that clients should set the `oauth2-server-uri` property to point at an OAuth server instead.[^spec]

## Credential vending and remote signing

The specification lets a catalog control access to the data files as well as the metadata. A client signals that it supports delegated access by sending the `X-Iceberg-Access-Delegation` header with one or both of the values `vended-credentials` and `remote-signing`. The server may supply access by any or none of the requested mechanisms.[^spec]

With **vended credentials**, the server returns storage credentials for Amazon S3, Azure Data Lake Storage, Google Cloud Storage or other stores in the `storage-credentials` field of the load-table response. Clients must check that field before looking for credentials in the table configuration. A separate route, `GET /v1/{prefix}/namespaces/{namespace}/tables/{table}/credentials`, loads fresh vended credentials for a table.[^spec]

With **remote signing**, the client does not receive credentials. Instead, it sends each object storage request to the catalog's `sign` route, and the catalog returns a signed request.[^spec] Project Nessie's documentation describes the trade-off: vending needs a security token service but adds no round trip per request, while signing works without one but adds a REST call for every storage request.[^nessie]

## Implementations

The table lists catalogs whose own documentation states that they implement the Iceberg REST catalog API. It is not complete.

| Catalog | License or type | Endpoint path | Storage access documented |
| --- | --- | --- | --- |
| [Apache Polaris](/wiki/Apache_Polaris) | Apache License 2.0[^n1] | See project docs | Vended credentials[^polaris] |
| [Unity Catalog](/wiki/Unity_Catalog) (open source) | Apache License 2.0[^n2] | `/api/2.1/unity-catalog/iceberg` | Vended credentials[^uc] |
| Lakekeeper | Apache License 2.0, written in Rust[^n3] | See project docs | Vended credentials for S3, ADLS and GCS; remote signing for S3[^n4][^n5] |
| Apache Gravitino | Apache License 2.0[^n6] | `/iceberg/` | Vended credentials for S3, GCS, OSS and ADLS; `remote-signing` is a configurable data access mode[^n7] |
| Project Nessie | Apache License 2.0[^n8] | `/iceberg` | Vended credentials and request signing; Iceberg REST support marked experimental[^nessie] |
| AWS Glue Data Catalog | Managed service | `/iceberg` on the regional Glue endpoint | S3 credentials vended for LoadTable; a subset of the REST operations[^glue] |

## Clients

Engines connect to a REST catalog through their Iceberg integration. [Trino](/wiki/Trino) selects it with `iceberg.catalog.type=rest` and uses vended credentials when `iceberg.rest-catalog.vended-credentials-enabled` is set to true (the default is false).[^n9] [DuckDB](/wiki/DuckDB) attaches a REST catalog with `ATTACH ... (TYPE iceberg)`, and attaching a catalog is required for writes.[^n10] [Apache Spark](/wiki/Apache_Spark) uses the Iceberg `SparkCatalog` with the catalog type set to `rest`.[^glue]

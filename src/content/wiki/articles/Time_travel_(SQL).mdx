**Time travel** in SQL is a query that reads a table as it was at an earlier version or point in time, written in [Apache Spark](/wiki/Apache_Spark) SQL as `SELECT ... FROM t VERSION AS OF v` or `SELECT ... FROM t TIMESTAMP AS OF ts`.[^grammar] Spark parses the clause, and the table format resolves it: [Delta Lake](/wiki/Delta_Lake) maps the version to a commit in its transaction log, and [Apache Iceberg](/wiki/Apache_Iceberg) maps it to a snapshot ID, branch or tag. Time travel is used to reproduce reports and models, audit changes and recover from bad writes, and it works only while the old data and metadata are still retained.[^delta]

## What is the syntax in Apache Spark?

The Spark SQL grammar accepts four spellings after a table name: `VERSION AS OF` and `FOR SYSTEM_VERSION AS OF` take an integer or string literal; `TIMESTAMP AS OF` and `FOR SYSTEM_TIME AS OF` take an expression.[^grammar] The timestamp expression must be deterministic and evaluable once at analysis time, and a query cannot carry both a version and a timestamp.[^ttspec]

Spark 3.3.0 added the `AS OF` syntax (SPARK-37219), and Spark 3.4.0 allowed a scalar subquery in the timestamp (SPARK-39306).[^r330][^r340] Spark 4.0.0 added time travel options to the `spark.read` API (SPARK-45575); the option names are `versionAsOf` and `timestampAsOf` by default, configurable with `spark.sql.timeTravelVersionKey` and `spark.sql.timeTravelTimestampKey`.[^r400][^sqlconf]

Spark 4.3.0 added an `@` suffix on table names (SPARK-57421, SPARK-58012): `name@v123` reads version 123, and `name@20240101000000000` (format `yyyyMMddHHmmssSSS`, in the session time zone) reads the table at that timestamp to millisecond precision. The suffix is controlled by `spark.sql.timeTravel.atSyntax.enabled`, default `true`.[^r430][^sqlconf] Also since 4.3, Spark rejects these time travel options on catalog-backed Data Source V2 writes with `UNSUPPORTED_FEATURE.TIME_TRAVEL`, because a write must target the current table state.[^migration]

## How does a connector implement time travel?

For catalog tables, Spark passes the parsed clause to the [catalog plugin](/wiki/Catalog_plugin_API_(Spark)). `TableCatalog` has `loadTable(ident, String version)` and `loadTable(ident, long timestamp)`, where the timestamp is in microseconds since the Unix epoch. Their default implementations throw a "no such table" error, so a catalog that does not override them does not support time travel.[^tablecatalog]

## Example

Spark SQL against a Delta Lake or Iceberg table named `sales.orders`:[^delta][^iceq][^sqlconf]

```sql
-- Delta Lake: commit version from DESCRIBE HISTORY
SELECT * FROM sales.orders VERSION AS OF 12;
SELECT * FROM sales.orders TIMESTAMP AS OF '2026-11-01 00:00:00';

-- Iceberg: snapshot ID, branch or tag name
SELECT * FROM lake.sales.orders VERSION AS OF 10963874102873;
SELECT * FROM lake.sales.orders VERSION AS OF 'audit-branch';

-- Spark 4.3 @ suffix (for catalogs that implement time travel)
SELECT * FROM sales.orders@v12;
```

The same reads with the DataFrame API, where `spark.read.table` passes its options to the relation that Spark resolves:[^reader][^r400]

```python
df_v12 = spark.read.option("versionAsOf", 12).table("sales.orders")
df_nov = spark.read.option("timestampAsOf", "2026-11-01 00:00:00").table("sales.orders")
```

## How do table formats compare?

|  | Delta Lake | Apache Iceberg | Apache Hudi |
| --- | --- | --- | --- |
| What a version is | A commit version in the transaction log, listed by `DESCRIBE HISTORY`[^delta] | A snapshot ID, or a branch or tag name[^iceq] | A commit time (instant)[^hudiqs] |
| Spark SQL syntax | `VERSION AS OF`, `TIMESTAMP AS OF`[^delta] | `VERSION AS OF`, `TIMESTAMP AS OF`, `FOR SYSTEM_VERSION AS OF`, `FOR SYSTEM_TIME AS OF`[^iceq] | `TIMESTAMP AS OF`[^hudisql] |
| Timestamp forms | Any expression castable to a timestamp, such as `'2018-10-18'` or `current_timestamp() - interval 12 hours`; no subqueries[^delta] | Timestamp string, or Unix time in seconds in SQL[^iceq] | `yyyy-MM-dd HH:mm:ss.SSS`, `yyyy-MM-dd` or `yyyyMMddHHmmssSSS`[^hudisql] |
| DataFrame options | `versionAsOf`, `timestampAsOf`[^delta] | `snapshot-id`, `as-of-timestamp` (milliseconds), `branch`, `tag`[^iceq] | `as.of.instant`[^hudiqs] |
| What limits how far back | `delta.logRetentionDuration` (default 30 days) and `VACUUM`, governed by `delta.deletedFileRetentionDuration` (default 7 days)[^delta] | Snapshot expiration; `history.expire.max-snapshot-age-ms` defaults to 5 days and `history.expire.min-snapshots-to-keep` to 1[^icecfg] | Not described on the cited Hudi pages |

Delta Lake documents that, by default, a table can be read up to 30 days back unless `VACUUM` has run or the retention properties were changed. Because version timestamps come from log file timestamps, time travel by timestamp can break if the table directory is copied to a new location, while time travel by version is unaffected.[^delta]

Iceberg branches and tags give names to snapshots. A query by snapshot ID or timestamp uses the schema of that snapshot, a query on a branch uses the table's current schema, and a query on a tag uses the schema of the tagged snapshot.[^iceq] Iceberg snapshots remain until they are expired, so expiration settings, not a fixed window, decide what can be read.[^icemaint]

## Time travel in other engines

| Engine | Syntax |
| --- | --- |
| [Trino](/wiki/Trino) 484 (Iceberg and Delta Lake connectors) | `FOR VERSION AS OF` and `FOR TIMESTAMP AS OF`; on Iceberg, the version can be a branch or tag name[^n1][^n2] |
| Snowflake | `AT` or `BEFORE` in the `FROM` clause, for example `AT (TIMESTAMP => ...)`[^n3] |
| BigQuery | `FOR SYSTEM_TIME AS OF`; the time travel window is seven days by default and can be set between two and seven days[^n4][^n5] |

A **Spark listener** is a class that [Apache Spark](/wiki/Apache_Spark) calls back when something happens inside an application, such as a job starting, a task ending, an executor being added or a SQL query finishing.[^listener] The core interface is `org.apache.spark.scheduler.SparkListener`; the SQL module adds `QueryExecutionListener` for completed queries, and [Structured Streaming](/wiki/Structured_Streaming) adds `StreamingQueryListener` for query progress. Listeners are how Spark builds its own [Spark UI](/wiki/Spark_UI) and [Spark event log](/wiki/Spark_event_log), and how external tools such as [OpenLineage](/wiki/OpenLineage) and [MLflow](/wiki/MLflow) observe Spark applications.

## How do Spark listeners work?

The driver posts every scheduler event to a **listener bus**, which delivers events to listeners on background threads, so that a slow listener does not block the scheduler. In Spark 4.3.0 the bus has separate queues: `shared` for user listeners, `appStatus` for the listener that feeds the Spark UI, `executorManagement` for dynamic allocation, and `eventLog` for the event log writer.[^bus]

Each queue has a fixed capacity, `spark.scheduler.listenerbus.eventqueue.capacity` (default 10000, since 2.3.0), which can be overridden for one queue with `spark.scheduler.listenerbus.eventqueue.<queueName>.capacity`.[^coreconf] When a queue is full, Spark drops events and logs an error saying that a listener is probably too slow to keep up.[^queue] Dropped events in the `appStatus` queue show up as missing or stuck jobs and stages in the UI, so listener code should return quickly.

## SparkListener

`SparkListener` is an abstract class with an empty method for each event, so a subclass overrides only what it needs. The methods include `onApplicationStart`, `onApplicationEnd`, `onJobStart`, `onJobEnd`, `onStageSubmitted`, `onStageCompleted`, `onTaskStart`, `onTaskEnd`, `onExecutorAdded`, `onExecutorRemoved`, `onEnvironmentUpdate` and `onOtherEvent`, which receives events from other modules such as SQL execution start and end.[^listener] The event classes are marked `@DeveloperApi`, and the underlying trait is documented as an internal interface that might change between releases; the source recommends extending `SparkListener` or `SparkFirehoseListener` instead of implementing it directly.[^listener]

A listener is registered in one of two ways:
- In configuration, with `spark.extraListeners` (since 1.3.0), a list of class names that Spark adds to the `SparkContext` when it starts. This catches events from the very start of the application.[^coreconf]
- In code, with `SparkContext.addSparkListener` and `removeSparkListener`.[^n1]

```scala
import org.apache.spark.scheduler.{SparkListener, SparkListenerStageCompleted}

class SlowStageListener extends SparkListener {
  override def onStageCompleted(e: SparkListenerStageCompleted): Unit = {
    val info = e.stageInfo
    for (start <- info.submissionTime; end <- info.completionTime if end - start > 60000) {
      println(s"Stage ${info.stageId} (${info.name}) took ${(end - start) / 1000}s")
    }
  }
}
// spark-submit --conf spark.extraListeners=com.example.SlowStageListener ...
```

## QueryExecutionListener

`org.apache.spark.sql.util.QueryExecutionListener` is called once per completed DataFrame or SQL action, with `onSuccess(funcName, qe, durationNs)` or `onFailure(funcName, qe, exception)`. The `QueryExecution` argument gives access to the logical and physical plans of the query.[^qel] The interface documentation notes that implementations must be thread-safe, because they can be called from several threads.

A query execution listener is registered per session with `spark.listenerManager.register(...)`, or for every new session with the static setting `spark.sql.queryExecutionListeners` (since 2.3.0).[^qel][^static] Internally, Spark delivers these callbacks from SQL execution end events on the listener bus.[^qel]

## StreamingQueryListener

`StreamingQueryListener` (since 2.0.0) receives `onQueryStarted`, `onQueryProgress` after each micro-batch, `onQueryIdle` (since 3.5.0) and `onQueryTerminated` for [Structured Streaming](/wiki/Structured_Streaming) queries.[^sql] It is registered with `spark.streams.addListener(...)` or the static setting `spark.sql.streaming.streamingQueryListeners` (since 2.4.0).[^static] PySpark has its own `StreamingQueryListener` class since 3.4.0, so a streaming listener can be written in Python:[^n2]

```python
from pyspark.sql.streaming import StreamingQueryListener

class ProgressLogger(StreamingQueryListener):
    def onQueryStarted(self, event):
        print(f"started {event.id}")
    def onQueryProgress(self, event):
        p = event.progress
        print(f"batch {p.batchId}: {p.numInputRows} rows")
    def onQueryIdle(self, event):
        pass
    def onQueryTerminated(self, event):
        print(f"terminated {event.id}")

spark.streams.addListener(ProgressLogger())
```

## What is built on Spark listeners?

- **The [Spark UI](/wiki/Spark_UI) and [Spark History Server](/wiki/Spark_History_Server).** Spark's status listener, on the `appStatus` queue, builds the data behind the UI, and the History Server replays event logs through the same kind of listener.[^bus][^n3]
- **The [Spark event log](/wiki/Spark_event_log)**, written by `EventLoggingListener` on the `eventLog` queue.[^bus][^n4]
- **[MLflow](/wiki/MLflow) autologging for Spark.** MLflow's `SparkDataSourceListener` extends `SparkListener` to detect data source reads, so that autologging can record which tables and paths a model was trained on.[^n5]
- **[OpenLineage](/wiki/OpenLineage) lineage collection.** The OpenLineage Spark integration is a `SparkListener`, `io.openlineage.spark.agent.OpenLineageSparkListener`, enabled with `spark.extraListeners`; it reads the events that the SparkContext emits and extracts metadata about jobs and datasets from the RDD and DataFrame dependency graphs.[^n6]

## Spark listener vs Spark plugin

A listener only observes events on the driver. A [Spark plugin](/wiki/Spark_plugin) runs code inside the driver and every executor, can register metrics, and can send messages from executors to the driver. Monitoring tools that need executor-side data use a plugin; tools that only need scheduler events use a listener.[^n7]

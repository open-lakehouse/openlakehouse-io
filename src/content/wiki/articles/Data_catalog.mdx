A **data catalog**, in a lakehouse, is the service that names tables and other data assets, records where each table's current metadata lives, coordinates commits, and decides who may read or write each asset. Engines ask the catalog which files make up a table and whether the current user may access them before they read any data. In an [open lakehouse](/wiki/Open_lakehouse), the catalog is reached through an open API, so that several engines share one view of the same tables. Open source examples include [Unity Catalog](/wiki/Unity_Catalog), [Apache Polaris](/wiki/Apache_Polaris) and other implementations of the [Iceberg REST catalog](/wiki/Iceberg_REST_catalog) specification.

## Role in a lakehouse

An [open table format](/wiki/Open_table_format) describes how one table is stored, but it does not say how a table is found by name or how concurrent writers agree on its current version. The catalog fills both gaps.

The Unity Catalog OSS documentation summarizes the catalog's job as answering three questions for an engine before it reads data: which files hold the table's data, whether the user may read them, and what the table's schema is.[^ucwhat]

For [Apache Iceberg](/wiki/Apache_Iceberg) tables, the Apache Polaris documentation states that a catalog must store the current metadata pointer for each table (a mapping from table name to the location of its current metadata file) and must update that pointer atomically when a new table version is committed.[^polaris-docs] This atomic swap is the basis of Iceberg's serializable isolation.[^icespec]

For [Delta Lake](/wiki/Delta_Lake) tables, the transaction log is stored alongside the data, so a table can be read without a separate metastore.[^deltaproto] The Delta protocol also defines catalog-managed tables, in which the managing catalog becomes the source of truth for whether a commit succeeded.[^deltaproto]

## Functions

A lakehouse catalog typically provides the following functions.

- **Namespace.** Assets are organized in a hierarchy. Unity Catalog uses a three-level namespace, `catalog.schema.asset`.[^ucwhat] The Iceberg REST catalog API organizes tables into namespaces.[^restyaml]
- **Metadata pointer and commits.** The catalog records each table's current version and accepts or rejects commits from writers.[^polaris-docs]
- **Access control.** With authentication and authorization enabled, Unity Catalog OSS checks ownership and privileges such as `USE_CATALOG`, `SELECT` and `MODIFY` on every request.[^ucwhat]
- **Credential vending.** The catalog issues short-lived storage credentials scoped to one table or volume, so that an engine can read or write only the data the user is allowed to access.[^ucwhat]
- **Discovery.** Because namespaces, tables and schemas are available over an API, engines and AI agents can list what exists instead of inferring it from storage paths.[^olio-agentic]

## The Iceberg REST catalog specification

<Hatnote>Main article: [Iceberg REST catalog](/wiki/Iceberg_REST_catalog)</Hatnote>

The Iceberg REST catalog specification is an OpenAPI definition of a catalog API for Iceberg tables. The Iceberg project created it because pluggable catalogs had to be implemented separately in every language, which made it hard for engines and commercial offerings to support many catalogs. With the REST protocol, a new language or engine needs only one client implementation to work with any compliant catalog.[^icerest]

The Iceberg documentation lists further benefits of the REST protocol: change-based commits that let the server resolve conflicts and retry, root metadata written by the catalog service, multi-table commits, lazy snapshot loading, and secure table sharing through credential vending or remote signing.[^icerest] The Iceberg documentation compares the role of the REST protocol to that of Hive's Thrift protocol for the Hive Metastore.[^icerest]

A client signals delegated storage access with the `X-Iceberg-Access-Delegation` request header. The defined values are `vended-credentials`, `remote-signing` and `none`, and the server may honor any or none of the requested mechanisms.[^restyaml]

## Catalogs and AI agents

In an [agentic lakehouse](/wiki/Agentic_lakehouse), the catalog is the main control point for AI agents. It tells an agent which tables exist and which it may touch, and it vends storage credentials scoped to the agent's identity, so that an agent can be limited to writing in its own sandbox namespace.[^olio-agentic]

## Limitations

A catalog governs only access that passes through it. The Unity Catalog OSS documentation warns that anyone holding direct storage credentials can bypass the catalog's checks, so the storage must also be locked down as part of a secure deployment.[^ucwhat]

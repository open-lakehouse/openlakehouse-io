**GPU acceleration in Spark** is the use of graphics processing units (GPUs) to run parts of an [Apache Spark](/wiki/Apache_Spark) application, either by scheduling GPUs to tasks that use them directly (for example deep learning training) or by replacing Spark SQL operators with GPU implementations. Apache Spark itself provides the first part: since Spark 3.0, its scheduler can request GPUs for executors and assign GPU addresses to tasks.[^r300][^conf] Running Spark SQL and DataFrame operators on a GPU needs a plugin such as the NVIDIA cuDF plugin for Apache Spark, formerly called the RAPIDS Accelerator for Apache Spark.[^dl]

## Comparison of GPU options for Spark

## How does Apache Spark schedule GPUs?

Apache Spark schedules GPUs as a custom resource named `gpu`. An application sets `spark.executor.resource.gpu.amount` (default 0) for GPUs per executor and `spark.task.resource.gpu.amount` for GPUs per task; fractional task amounts let several tasks share one GPU. On YARN and Kubernetes, the executor also needs `spark.executor.resource.gpu.discoveryScript`, and Kubernetes needs `spark.executor.resource.gpu.vendor`, for example `nvidia.com`.[^conf] Spark then assigns GPU addresses to each task, which user code reads with `TaskContext.get().resources()`.[^conf] Since Spark 3.1, [Spark resource profiles](/wiki/Spark_resource_profiles) let one stage request GPU executors while other stages use CPU-only executors.[^conf]

Spark's own GPU support is used by machine learning code inside Spark. `pyspark.ml.torch.distributor.TorchDistributor`, added in Spark 3.4.0, runs distributed PyTorch training on Spark; with `use_gpu=True` (the default) on a cluster it requires `spark.task.resource.gpu.amount` of at least 1.[^torch]

## What is the NVIDIA cuDF plugin for Apache Spark?

The NVIDIA cuDF plugin for Apache Spark is a set of Spark plugins, built on the cuDF library and UCX, that run DataFrame and SQL processing on NVIDIA GPUs. NVIDIA renamed it from the RAPIDS Accelerator for Apache Spark; the GitHub repository moved from `NVIDIA/spark-rapids` to `NVIDIA/cudf-spark`, and the artifact name `rapids-4-spark` stays the same for now.[^dl][^readme] The plugin hooks into Spark at the Catalyst level, after the language APIs have been converted to a DataFrame plan, so it applies to PySpark, Scala, Java and SQL alike.[^faq]

The cuDF plugin is turned on with `spark.plugins=com.nvidia.spark.SQLPlugin`. NVIDIA's on-premise example combines it with Spark's own GPU settings, `spark.executor.resource.gpu.amount=1` and `spark.task.resource.gpu.amount=0.25`.[^onprem] The getting-started guide asks for Apache Spark 3.3 or later and one GPU per executor.[^overview]

```bash
spark-submit \
  --jars rapids-4-spark_2.13-26.10.0.jar \
  --conf spark.plugins=com.nvidia.spark.SQLPlugin \
  --conf spark.executor.resource.gpu.amount=1 \
  --conf spark.task.resource.gpu.amount=0.25 \
  --conf spark.rapids.sql.explain=NOT_ON_GPU \
  app.py
```

### Which operators and formats run on the GPU?

The cuDF plugin replaces physical operators such as `FileSourceScanExec`, `FilterExec`, `ProjectExec`, `HashAggregateExec`, `SortExec`, `WindowExec`, `ShuffleExchangeExec`, `BroadcastHashJoinExec`, `ShuffledHashJoinExec` and `SortMergeJoinExec`, and pandas UDF operators such as `MapInPandasExec`.[^ops] Its supported-operators page lists GPU reads for Avro, CSV, [Delta Lake](/wiki/Delta_Lake), Hive text, [Apache Iceberg](/wiki/Apache_Iceberg), JSON, ORC and [Apache Parquet](/wiki/Apache_Parquet), and GPU writes for Delta Lake, Hive text, Iceberg, ORC and Parquet. Timestamps are supported only in the UTC time zone.[^ops]

The cuDF plugin's FAQ states that only a limited set of SQL and DataFrame operations is supported; some MLlib functions such as PCA are accelerated, while GraphX and RDD code are not. Dataset operations that take Scala or Java functions, such as `flatMap` or `foreachPartition`, still run correctly but mostly on the CPU.[^faq]

### What happens when an operator is not supported?

When the cuDF plugin cannot run an operation on the GPU, that part of the plan runs on the Spark CPU implementation, so the query still completes.[^overview] The plugin decides this with rules, not the Spark scheduler.[^faq] `spark.rapids.sql.enabled` (default true) turns GPU SQL on or off, and `spark.rapids.sql.explain` logs the parts of a plan that were not placed on the GPU, for example with the value `NOT_ON_GPU`.[^configs]

## What other GPU options exist for Spark?

[Apache Gluten](/wiki/Apache_Gluten), a project that offloads Spark SQL execution to native engines such as [Velox](/wiki/Velox), documents an experimental GPU path on its main branch: with `spark.gluten.sql.columnar.cudf=true`, Velox plan nodes are converted to GPU operators built on cuDF, and unsupported operators fall back to the CPU.[^glutengpu] See [Native execution engine (Spark)](/wiki/Native_execution_engine_(Spark)) for CPU-based native engines.

cuML Spark (repository `NVIDIA/cuml-spark`) provides PySpark ML compatible algorithms on GPUs, including KMeans, LinearRegression, LogisticRegression, PCA, RandomForestClassifier and UMAP.[^cumlspark]

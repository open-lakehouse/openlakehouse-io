**Apache Airflow** is an open source platform for developing, scheduling and monitoring workflows, such as batch data pipelines and machine learning jobs, in which each workflow is defined as Python code.[^index] Airflow does not process data itself; it decides when tasks run, in what order, and what happens when they fail. In an [open lakehouse](/wiki/Open_lakehouse), Airflow commonly starts the [Apache Spark](/wiki/Apache_Spark) jobs and other steps that load and transform tables.

## Concepts

An Airflow workflow is a **Dag** (directed acyclic graph): a model that holds everything needed to run a workflow, including its schedule, its tasks and the dependencies between them, and callbacks for when it completes.[^index] Because Dags are Python code, they can be generated dynamically and parameterized.[^index]

Each step in a Dag is a **task**, usually created from an **operator**, a reusable template for one kind of work such as running a shell command or submitting a Spark job. Operators for external systems are shipped in separately versioned **provider** packages.[^spark-ops]

## Architecture

In Airflow 3.4, a minimal installation has the following required components:[^arch]

- a **scheduler**, which triggers scheduled workflows and submits tasks to the **executor** (a configuration of the scheduler that runs inside the scheduler process, not a separate component);
- a **Dag processor**, which parses Dag files from a **Dag bundle** and stores them in serialized form in the metadata database;
- an **API server**, which serves the REST API and the user interface, and through which tasks report their state back to Airflow without direct database access;
- a **metadata database**, usually PostgreSQL or MySQL, which stores the state of tasks, Dags and variables.

Optional components include **workers** (for example long-running processes with the CeleryExecutor, or pods with the KubernetesExecutor), a **triggerer** that runs deferred tasks in an asyncio event loop, and a plugins folder.[^arch]

## History

Maxime Beauchemin started Airflow at Airbnb in October 2014. It was open sourced on Airbnb's GitHub and announced in June 2015. The project entered the Apache Incubator in March 2016, and the ASF announced Apache Airflow as a top-level project in January 2019.[^n1]

Airflow 2.0.0 was published on 17 December 2020 and Airflow 3.0.0 on 22 April 2025.[^pypi] Airflow 3 introduced the Task Execution Interface (AIP-72), which moves Airflow toward a client-server architecture with an API server and a Python Task SDK, along with Dag versioning, a new React-based user interface and event-driven scheduling on data assets.[^n2] The latest release on 22 November 2026 is Airflow 3.4.0, released on 6 November 2026.[^n3]

## Orchestrating Apache Spark

Airflow runs Spark through the `apache-airflow-providers-apache-spark` provider package. Its latest version on 22 November 2026 is 6.3.4, published on 24 October 2026; it requires Airflow 2.11.0 or later and Python 3.11 or later.[^n4][^pyproject] Version 6.3.4 contains these operators:[^spark-ops][^src]

| Operator | Module | What it does |
| --- | --- | --- |
| `SparkSubmitOperator` | `operators.spark_submit` | Wraps the `spark-submit` binary to launch an application; the default connection is `spark_default`. |
| `SparkSqlOperator` | `operators.spark_sql` | Runs a Spark SQL query through the `spark-sql` binary. |
| `SparkJDBCOperator` | `operators.spark_jdbc` | Extends `SparkSubmitOperator` to move data between Spark and JDBC databases. |
| `PySparkOperator` | `operators.spark_pyspark` | Runs a Python function that receives a Spark session, locally or against a [Spark Connect](/wiki/Spark_Connect) server; also available as the `@task.pyspark` decorator. |
| `SparkPipelinesOperator` | `operators.spark_pipelines` | Wraps the `spark-pipelines` CLI to run or dry-run a [Spark Declarative Pipelines](/wiki/Spark_Declarative_Pipelines) project. |

`PySparkOperator` became available as an operator in provider 5.5.0, and `SparkPipelinesOperator` was added in 5.6.0.[^changelog] `SparkPipelinesOperator` takes a `pipeline_spec` path and a `pipeline_command` of `run` (the default) or `dry-run`.[^n5]

The following Dag, for Airflow 3.4 with provider 6.3.4, checks a declarative pipeline with a dry run, runs it, and then submits a Spark application:

```python
from datetime import datetime

from airflow.sdk import DAG
from airflow.providers.apache.spark.operators.spark_pipelines import SparkPipelinesOperator
from airflow.providers.apache.spark.operators.spark_submit import SparkSubmitOperator

with DAG(
    dag_id="lakehouse_daily",
    schedule="@daily",
    start_date=datetime(2026, 11, 1),
    catchup=False,
):
    check = SparkPipelinesOperator(
        task_id="pipeline_dry_run",
        pipeline_spec="/opt/pipelines/sales/spark-pipeline.yml",
        pipeline_command="dry-run",
    )
    run = SparkPipelinesOperator(
        task_id="pipeline_run",
        pipeline_spec="/opt/pipelines/sales/spark-pipeline.yml",
    )
    report = SparkSubmitOperator(
        task_id="build_report",
        application="/opt/jobs/build_report.py",
    )

    check >> run >> report
```

## Use in an open lakehouse

Airflow sits above the engines in an [open lakehouse](/wiki/Open_lakehouse). It can order ingestion, transformation and maintenance jobs that run on Spark, [Trino](/wiki/Trino) or other engines against tables in [Apache Iceberg](/wiki/Apache_Iceberg) or [Delta Lake](/wiki/Delta_Lake) format. With [Spark Declarative Pipelines](/wiki/Spark_Declarative_Pipelines), the division of work is that SDP orders the datasets inside one pipeline, while Airflow schedules the pipeline as a whole and connects it to work outside Spark.

<Status level="active">Project Tungsten is not deprecated in any Spark release. It was a performance initiative, not a feature with an on/off switch; its code is the default execution path in Spark 4.3.0. Only its old configuration flag, `spark.sql.tungsten.enabled`, was deprecated (Spark 1.6.0) and later dropped.[^mm430]</Status>

**Project Tungsten** is the name of an [Apache Spark](/wiki/Apache_Spark) engineering initiative, started in 2015, to make Spark's execution more efficient in CPU and memory by managing memory explicitly, storing rows in a compact binary format, using CPU caches better and generating code at run time.[^jira7075] Tungsten is not a separate engine or a module that can be installed or turned off: its results (for example the `UnsafeRow` format, Tungsten-managed memory pages and whole-stage code generation) are part of how Spark SQL and DataFrame queries run in every current release. The name survives mostly in source code, configuration aliases and older documentation.

## What the name referred to

The umbrella ticket SPARK-7075, "Project Tungsten (Spark 1.5 Phase 1)", states the premise: most Spark workloads observed by its authors were bottlenecked by CPU and memory rather than by I/O or network. It names three areas of work:[^jira7075][^blog2015]

- **Memory management and binary processing.** Keep data in a binary format instead of as Java objects, to reduce garbage collection overhead and memory use; account for memory in bytes; and let operators that know the data types work directly on the binary data without serialization.
- **Cache-aware computation.** Algorithms and data structures, such as sorting and hashing, laid out to make better use of CPU caches.
- **Code generation.** Generate code at run time for expression evaluation and serialization, to use modern compilers and CPUs better.

The work arrived over several releases. The Spark 1.4.0 release notes list SPARK-7081, a faster sort-based shuffle path, as "Initial performance improvements in project Tungsten".[^r140][^n1] Phase 1 (SPARK-7075) has fix version 1.5.0, and the 1.5.0 release notes say that optimized execution with manually managed memory (Tungsten) was now on by default, together with code generation for expression evaluation.[^jira7075][^r150] A phase 2 umbrella followed (SPARK-9697).[^n2] Whole-stage code generation (SPARK-12795) shipped in Spark 2.0.0, and a 2016 Databricks post by Spark developers presented it as the core of a "second generation Tungsten engine".[^jira12795][^blog2016] The Spark 2.0.0 release notes describe whole-stage code generation without using the Tungsten name.[^n3]

## What remains in Spark 4

Project Tungsten has no deprecation or removal in any Spark release. Its pieces are ordinary parts of the engine:

- **Tungsten memory.** Spark's memory manager still allocates "Tungsten" memory pages for sorting, hashing and shuffle, on the JVM heap by default or off-heap through `sun.misc.Unsafe` when `spark.memory.offHeap.enabled` is true (default false, available since 1.6.0).[^mm430][^tmm430][^conf430] See [Spark memory management](/wiki/Spark_memory_management).
- **The `UnsafeRow` format.** Spark SQL's internal row format is backed by raw memory instead of Java objects: a null-tracking bit set, one 8-byte word per field, and a variable-length region for strings and other variable-length values.[^unsaferow]
- **Whole-stage code generation.** Enabled by default through the internal setting `spark.sql.codegen.wholeStage` (default true, since 2.0.0). In `EXPLAIN` output, an operator compiled into a generated stage is prefixed with `*(n)`, where n is the code generation stage ID.[^sqlconf430][^wscg430] See [Whole-stage code generation](/wiki/Whole-stage_code_generation).
- **The `tungsten-sort` shuffle alias.** Spark 1.5.0 mapped `spark.shuffle.manager=tungsten-sort` to a separate `UnsafeShuffleManager`. SPARK-10708 merged it into the sort shuffle manager in 1.6.0, and since then `tungsten-sort` is an alias for `SortShuffleManager`, as it still is in 4.3.0.[^env150][^n4][^sm430]

### The `spark.sql.tungsten.enabled` flag

The one Tungsten item that was deprecated is a configuration flag. In Spark 1.5.0, `spark.sql.tungsten.enabled` (default true) switched the Tungsten execution backend and code generation on or off.[^r150][^n5] Spark 1.6.0 removed the option to turn off the unsafe (Tungsten) and code generation paths (SPARK-11644)[^n6] and moved the flag to a list of deprecated keys: setting it logged a warning that the property "is deprecated and will be ignored. Tungsten will continue to be used."[^n7] By Spark 2.0.0 the `SET` command no longer has any special handling for it.[^n8] There has been no way to turn Tungsten off as a whole since 1.6.0.

## Example

This PySpark query runs a filter and an aggregation. After the query has run, `explain()` shows the final adaptive plan, where the `*(1)` prefix marks the three operators that were compiled together into one generated function.

```python
df = spark.range(1000).filter("id % 2 = 0").selectExpr("sum(id)")
df.collect()
df.explain()
```

Part of the output from a Spark 4.3 build:

```
   ResultQueryStage 0
   +- *(1) HashAggregate(keys=[], functions=[sum(id#0L)])
      +- *(1) Filter ((id#0L % 2) = 0)
         +- *(1) Range (0, 1000, step=1, splits=1)
```

## What Tungsten is not

- **Not the optimizer.** The [Catalyst optimizer](/wiki/Catalyst_optimizer) decides what plan to run; Tungsten work concerns how the chosen physical operators use memory and CPU. The MLlib guide, for example, lists "Tungsten and Catalyst optimizations" as benefits of DataFrames.[^n9]
- **Not a native engine.** Tungsten code runs in the JVM and generates Java code. Native execution engines for Spark, such as Apache Gluten (with Velox) and Apache DataFusion Comet, replace JVM operators with native code; Photon is a proprietary Databricks engine. See [Native execution engine (Spark)](/wiki/Native_execution_engine_(Spark)).
- **Not available to RDD code.** The binary row format and generated code apply to DataFrame, Dataset and SQL operators, which know the data types. Programs that use the [RDD](/wiki/RDD) API with arbitrary JVM objects do not get these benefits.[^jira7075]

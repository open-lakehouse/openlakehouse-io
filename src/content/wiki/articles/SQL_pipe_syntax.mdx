**SQL pipe syntax** is an extension of SQL in which a query is written as a sequence of operators joined by the pipe symbol `|>`, each operator taking the table produced by the previous one, so that the query reads top to bottom in the order of its logical transformations. [Apache Spark](/wiki/Apache_Spark) SQL supports pipe syntax since Spark 4.0.0 (SPARK-49555).[^r400][^doc] Pipe syntax keeps standard SQL working unchanged: a query can use standard clauses, pipe operators, or both.[^doc]

## Where does SQL pipe syntax come from?

Pipe syntax was described by Jeff Shute and other Google engineers in the paper "SQL Has Problems. We Can Fix Them: Pipe Syntax In SQL", published in the Proceedings of the VLDB Endowment, volume 17, issue 12 (2024). The paper presents it as an addition to GoogleSQL, Google's SQL dialect, that fixes the rigid clause order of standard SQL without replacing the language.[^paper] BigQuery documents pipe syntax as an extension to GoogleSQL, and Google announced that it would be available to all BigQuery users by default from 4 February 2025.[^bq][^bqblog] The Spark ticket SPARK-49555 links to the paper and to the open source ZetaSQL implementation.[^jira]

## How does pipe syntax work in Spark SQL?

A pipe query in Spark SQL usually starts with `FROM table_name`, which Spark accepts as a standalone query equivalent to `TABLE table_name`. Any number of pipe operators can follow, in any order, each starting with `|>` and one or more SQL keywords.[^doc] Pipe operators can also be appended to the end of any ordinary Spark SQL query.[^doc]

Spark's documentation states several invariants. Each operator works the same way on its input regardless of how that input was computed. For a valid chain of N operators, the first M operators (M ≤ N) also form a valid query, which lets a user run a prefix of a query while debugging. Subqueries, views and DDL or DML statements can contain queries in either syntax.[^doc]

Pipe syntax is controlled by `spark.sql.operatorPipeSyntaxEnabled`, added in Spark 4.0.0 and `true` by default in Spark 4.3.0.[^sqlconf] Since Spark 4.2.0 a single `|` can also be used as the pipe token (SPARK-51518). This is governed by `spark.sql.parser.singleCharacterPipeOperator.enabled`, true by default; the parser tells a pipe apart from bitwise OR by checking whether a pipe operator keyword follows.[^r420][^sqlconf][^grammar]

## Which pipe operators does Spark SQL support?

| Operator | What it does | Closest standard Spark SQL |
| --- | --- | --- |
| `SELECT` | Evaluates expressions over each input row | Outermost `SELECT` of a subquery |
| `EXTEND` | Appends computed columns | `SELECT *, expr AS col` |
| `SET` | Replaces the values of existing columns | `SELECT * REPLACE (expr AS col)` |
| `DROP` | Removes columns | `SELECT * EXCEPT (col)` |
| `AS` | Gives the input a new table alias | Table alias |
| `WHERE` | Filters rows; can appear anywhere, so no separate `HAVING` or `QUALIFY` is needed | `WHERE`, `HAVING`, `QUALIFY` |
| `AGGREGATE` | Aggregates, with or without `GROUP BY` | `SELECT ... GROUP BY` |
| `JOIN` | Joins the input (left side) with a table argument (right side) | `JOIN` |
| `ORDER BY`, `LIMIT` | Sorts and limits rows | `ORDER BY`, `LIMIT` |
| `UNION`, `INTERSECT`, `EXCEPT` | Set operations with another table | Same set operations |
| `TABLESAMPLE`, `PIVOT`, `UNPIVOT` | Sampling and reshaping | Same clauses |

Source: Spark 4.3.0 pipe syntax documentation.[^doc]

`AGGREGATE` differs most from standard SQL. Its output holds the grouping columns first and then the aggregate columns, so the grouping expressions are not repeated in a `SELECT` list. `GROUP BY` ordinals refer to the columns of the input table, not to a select list.[^doc] In Spark 4.3.0 a pipe `SELECT` also accepts aggregate functions and an optional `GROUP BY`, as in `TABLE t |> SELECT a, SUM(b) AS s GROUP BY a`: the grammar allows a `GROUP BY` clause after the select list, the analyzer permits aggregate functions in `SELECT` but rejects them in `EXTEND`, `SET` and other pipe operators, and the Spark test suite runs such queries.[^grammar][^pipeops][^pipetests] The Spark 4.2.0 release notes list this change as SPARK-54292.[^r420] The 4.3.0 pipe syntax documentation still says that aggregate functions are not supported in a pipe `SELECT` and should go in `AGGREGATE`.[^doc]

## Example

The Spark documentation rewrites query 13 of the TPC-H benchmark, which in standard SQL needs a subquery for its two levels of aggregation, as a straight sequence of operators:[^doc]

```sql
-- Standard SQL
SELECT c_count, COUNT(*) AS custdist
FROM (
  SELECT c_custkey, COUNT(o_orderkey) c_count
  FROM customer
  LEFT OUTER JOIN orders ON c_custkey = o_custkey
    AND o_comment NOT LIKE '%unusual%packages%'
  GROUP BY c_custkey
) AS c_orders
GROUP BY c_count
ORDER BY custdist DESC, c_count DESC;

-- The same query with pipe syntax
FROM customer
|> LEFT OUTER JOIN orders ON c_custkey = o_custkey
   AND o_comment NOT LIKE '%unusual%packages%'
|> AGGREGATE COUNT(o_orderkey) c_count
   GROUP BY c_custkey
|> AGGREGATE COUNT(*) AS custdist
   GROUP BY c_count
|> ORDER BY custdist DESC, c_count DESC;
```

A smaller example builds columns step by step and filters on an aggregate without `HAVING`:

```sql
VALUES ('a', 10), ('a', 5), ('b', 3) AS t(k, v)
|> EXTEND v * 2 AS v2
|> AGGREGATE SUM(v2) AS total GROUP BY k
|> WHERE total > 10
|> ORDER BY total DESC;
-- one row: k = 'a', total = 30
```

## Is pipe syntax more readable?

The paper's authors argue that standard SQL's fixed clause order forces subqueries and "inside-out" data flow, and that operators applied in sequence are easier to read, write and extend.[^paper] In Spark SQL, pipe syntax also lets a computed column be used by the next operator without a lateral column alias or a subquery.[^doc] Pipe syntax is optional: any query can be written in standard Spark SQL, in pipe syntax or in a mix of the two, so it can be adopted one query at a time.[^doc]
